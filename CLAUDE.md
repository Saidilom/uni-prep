# CLAUDE.md

Инструкции для Claude Code / AI-агентов, работающих в этом репозитории.

## Прежде чем писать миграцию

**Не доверяй объявленному в SQL типу колонки.** `public.users.id` объявлен как `text` в `001_init.sql`, но многие более ранние миграции ссылались на него как на `uuid` — реальность подтверждай командой:

```bash
supabase db query --linked "select column_name, data_type from information_schema.columns where table_name = 'X';"
```

RLS-политики, сравнивающие `auth.uid()` (uuid) напрямую с текстовой колонкой, падают с ошибкой Postgres `42883` — и эта ошибка **не** трактуется как `false`, она обрывает весь запрос. Паттерн, который проверен и работает: `auth.uid()::text = user_id`, и для admin/teacher-проверок — SECURITY DEFINER-функции `public.is_admin()` / `public.is_teacher()` (миграции 004, 010), которые сами делают каст и заодно не дают RLS войти в рекурсию через себя же.

## Конвенции миграций

- Каждый файл — `NNN_описание.sql`, следующий номер по порядку.
- Всегда заканчивай миграцию, меняющую схему, `NOTIFY pgrst, 'reload schema';` — иначе PostgREST продолжит отдавать старую схему до перезапуска.
- Меняешь возвращаемые колонки функции (`RETURNS TABLE`) — `CREATE OR REPLACE` этого не позволяет, нужен `DROP FUNCTION` перед `CREATE FUNCTION`.
- Триггер, который висит и на INSERT, и на UPDATE — в `WHEN`-условии нельзя ссылаться на `OLD` (его ещё не существует для INSERT), даже если логика внутри проверяет `TG_OP`. Разделяй на два триггера.
- Перед `DROP`/деструктивным `ALTER` на таблице с потенциальными данными — проверь через `supabase db query --linked`, реально ли она пустая/неиспользуемая, не полагайся на то, что "она не должна использоваться".

## Паттерн: банк вопросов копирует, а не ссылается

`question_bank` — источник для авторства вопросов, но `placement_questions`/`mock_questions` хранят **копию** содержимого вопроса на момент добавления в тест (плюс `bank_id` для отслеживания происхождения), а не живую FK-ссылку. Осознанное решение: правка вопроса в банке не должна задним числом менять правильный ответ уже пройденного учеником теста.

## Паттерн: приватность Placement

По решению из `PLAN-REGISTAN-V3.md` (Решение §1) — Placement/Diagnostic тест никому не показывает разбор по вопросам, даже админу/учителю, только итоговый %. `submit_placement` не строит и не сохраняет по-вопросный разбор вообще. Если добавляешь что-то новое к Placement — не создавай механизм, который бы это обошёл.

## Аудит-лог

`audit_log` заполняется **только** Postgres-триггерами (миграция `015_audit_log.sql`), не кодом приложения — так событие попадёт в лог при любом пути изменения данных. У таблицы нет INSERT-политики ни для одной роли. Если добавляешь новое критическое действие для аудита — добавляй триггер на соответствующую таблицу, не вызов из клиента/route handler.

## `@supabase/supabase-js` 2.111+ и `supabase.from<T>()`

Синтаксис `supabase.from<Row>("table")` с одним generic-аргументом сломан в этой версии (требует 2 аргумента). По всему репозиторию принят единый паттерн: `supabase.from("table").select("*")` без generic, с ручным `as Type[]`/`as Type` после получения `data`. Не возвращай старый синтаксис.

## Тесты

`npm test` (Vitest) — юнит-тесты только для чистой логики без сети/БД: `src/lib/rasch.ts`, `src/lib/registan-utils.ts` (`userHasMockAccess`), `src/lib/payment-rules.ts`. Если выносишь новую decision-логику из API route/компонента — выноси её в отдельный чистый модуль в `src/lib/`, как это уже сделано с `payment-rules.ts`, и добавляй тест рядом (`*.test.ts`). `vitest.config.mts` подставляет фейковые `NEXT_PUBLIC_SUPABASE_*` переменные — модули, которые на верхнем уровне создают Supabase-клиент, импортируются нормально, но реальных сетевых вызовов тесты не делают.
