- Осталось сделать (не входит в Приоритет 0): прогнать `supabase db push` на staging/prod и убедиться, что constraint реально применяется на реальных данных.

### 1.2 Баг сортировки в `registan-utils.ts` ✅

## 4. Приоритет 3 — Оплата: мок-версия ✅ Выполнено, реальный провайдер — отдельная будущая задача

Решение: не ждать выбора провайдера (Payme/Click/Uzum), а реализовать полный цикл покупки с мок-оплатой, чтобы флоу «покупка → доступ → видно в админке» можно было тестировать уже сейчас. Архитектура специально сохраняет форму, в которую позже встанет реальный провайдер.

- `src/lib/supabase/server.ts` — добавлен `createRouteHandlerClient()`: cookie-based клиент через `@supabase/ssr` для Route Handlers (по паттерну из `middleware.ts`); нужен, чтобы API-роуты знали текущего пользователя по сессионной cookie, не доверяя `userId` из тела запроса. Существующий `supabaseServer` (service-role) не тронут.
- `src/app/api/payments/create/route.ts` — проверяет пользователя и что тест `type='paid'`, сумму берёт из `mock_tests.price` на сервере (не от клиента), переиспользует уже существующий `pending`-платёж вместо дубликата, создаёт `payments` (`provider: "mock"`) через service-role клиент (RLS разрешает запись в `payments`/`mock_access` только через `service_role` — прямая вставка с anon-ключа невозможна).
- `src/app/api/payments/mock-confirm/route.ts` — намеренно **не** `webhook`, имя явно маркирует временность. Принимает `{ paymentId, outcome }`, идемпотентно переводит платёж в `success`/`cancelled`, при успехе создаёт `mock_access` (`source: "payment"`). Когда появится реальный провайдер — файл заменяется на настоящий `/api/payments/webhook` с проверкой подписи.
- `src/app/mock/pay/[paymentId]/page.tsx` — «мок-касса»: явный баннер «Тестовый режим оплаты», кнопки «Оплатить (тестовый режим)» / «Отменить».
- `src/app/mock/page.tsx` — кнопка «Купить» для заблокированных платных тестов теперь реально работает (раньше вела на мёртвую ссылку `/`).

**Что остаётся для реального провайдера** (будущая задача, зависит от ответа заказчика):
- Выбрать Payme/Click/Uzum, завести `.env.example` с ключами.
- `create` router: вместо возврата `paymentId` на свою мок-страницу — редирект на хостинг провайдера.
- `mock-confirm` → полноценный `/api/payments/webhook` с проверкой подписи провайдера.
- `/mock/pay/[paymentId]` становится не нужен (или остаётся как fallback для дебага).

## 6. Приоритет 5 — Тестирование и деплой

Сквозные сценарии, которые должны проходить end-to-end перед релизом:

1. QR (`/join?source=reception`) → «Войти через Google» → онбординг (имя/фамилия/телефон) → пользователь появляется в `/admin/users` с `registeredvia='qr'`.
2. Админ создаёт Placement-шаблон в `/admin/placement`, назначает его пользователю → пользователь видит уведомление (realtime toast) → проходит тест на `/placement/[id]` → результат виден в `/admin/placement/results` с детализацией по вопросам.
3. Админ выдаёт статус «Ученик Registan» в `/admin/registan` → пользователь видит бесплатные Mock в `/mock` → проходит → результат сохраняется, таймер реально считает время.
4. Обычный (не-Registan) пользователь пытается пройти платный Mock → видит «Купить» → мок-касса (`/mock/pay/[paymentId]`) → «Оплатить (тестовый режим)» → `mock_access` создаётся → тест открывается → запись видна в `/admin/payments` со статусом «Успешно» и provider `mock`.

Технические проверки:
- RLS: попытка прочитать `correct_answer` напрямую с anon-ключа → должно быть невозможно (только через `get_placement_questions`/`get_mock_questions`).
- RPC `submit_placement`/`submit_mock` без авторизации → ошибка.
- `supabase db push` на staging проходит без ошибок после исправления FK (см. 1.1).
- Env-переменные и webhook URL прописаны в Vercel; QR в `/admin/qr` генерируется с production-доменом.
