6. **№16 — Уровни A+/A/B+/B/C+/C.** ✅ Готово. Уточнили с пользователем: это не проценты — это уже существующая Rasch-логика (сложность вопроса считается по тому, как массово ошибались ученики), стандартизированная на шкалу /75 относительно КОГОРТЫ сдававших именно этот мок (как уже было сделано для английского CEFR, но там — отдельный official-scale расчёт). Реализация: вынес `mean`/`stdev`/`raschThetaToT` из `english-cefr.ts` в `src/lib/rasch.ts` (это generic-математика, а не English-специфика), новый `src/lib/mock-grade-level.ts` (`gradeLevelFromScore`, чистая функция, с тестами), `mock_results.level_score`/`grade_level` (миграция `034_mock_grade_level.sql`), `/api/rasch/recalculate` — который уже вызывается после КАЖДОГО мока любого предмета — теперь дополнительно считает Z-стандартизацию по своей же уже посчитанной θ и уровень. Бейджи добавлены на экран результата, в список результатов ученика и в учительский просмотр результатов мока. ⚠️ Важный нюанс: при малом числе сдававших (особенно первый/единственный человек) шкала не может себя стандартизировать и уровень уедет к центру (50 → C+) независимо от реального результата — это статистически ожидаемо (нужна реальная когорта), но стоит иметь в виду и, возможно, явно скрывать уровень при слишком малой выборке.

### Этап 5 — расписание и автоматизация ✅ выполнено

14. **№5 — Начало/окончание теста + отложенная публикация результатов.** ✅ Готово. Уточнили с пользователем реальный сценарий: относится **только к платным (админским) мокам**, бесплатные/`class_only` не затрагиваются вообще. Изначально окно входа считалось автоматически (1 час от `starts_at` + длительность мока) — по повторной просьбе пользователя переделано на **полностью ручной интервал**: админ при публикации указывает и `starts_at`, и `ends_at` (любой промежуток — хоть пара часов, хоть несколько дней). Вход в тест закрыт вне этого окна; кто ещё решает, когда наступает `ends_at`, — досдаётся автоматически с текущими ответами (таймер мока на клиенте сам подстраивается под более раннее из двух: обычная длительность или дедлайн). После сдачи ученик не видит балл сразу — видит «Ответы приняты, результаты объявят {дата}» до отдельно заданного `results_publish_at`. Миграция `047_manual_mock_end_time.sql` заменила деривированную формулу на явную колонку `ends_at` (обязательна вместе с `starts_at`, `publish_imported_mock` это валидирует) — весь текст ниже про «1 час» описывает уже неактуальный первый вариант, оставлен для истории.

    Финальная архитектура оказалась **проще**, чем предполагал первоначальный вопрос про `pg_cron` vs Vercel Cron — **никакой cron-джобы не понадобилось вообще**: и окно входа, и момент публикации — это чистое сравнение `now()` с датой в момент запроса, а не событие, которое надо кому-то "выполнить". Рекомендованный пользователем `pg_cron` был бы нужен только если бы требовался пересчёт/действие в момент дедлайна (например, форс-финализация Rasch по всей когорте) — но это уже и так происходит: `/api/rasch/recalculate` пересчитывает уровень по ВСЕМ результатам мока при каждой новой сдаче, так что к моменту публикации данные уже посчитаны по полной когорте.

    Изменения:
    - `038_mock_schedule_columns.sql` — `mock_tests.starts_at`/`results_publish_at`.
    - `039_can_access_mock_schedule_window.sql` — `can_access_mock()` (единая точка входа для RLS на `mock_tests`/`mock_sections` и для проверки внутри `submit_mock`) теперь пускает только если: мок бесплатный, `starts_at` не задан, `now()` внутри `[starts_at; starts_at + 1ч + duration_minutes]` (щедрый запас — иначе ученик, начавший под конец часа входа, потерял бы доступ на середине теста при простом обновлении страницы), либо у ученика уже есть результат (просмотр уже сданного — всегда без ограничения по времени).
    - `040_submit_mock_results_gate.sql` — `submit_mock` теперь не возвращает `score`/`percentage`/`level`/`sectionScores` в ответе, если `results_publish_at` в будущем — вместо этого `resultsPending: true` + сама дата. Подсчёт и запись в БД происходят как обычно (учитель/админ видят результат сразу), скрывается только то, что летит обратно **самому ученику**.
    - `041_publish_imported_mock_schedule.sql` — админ задаёт обе даты прямо в мастере публикации (`mock-test-studio.tsx`, два `datetime-local` поля, видны только когда `mode==="admin" && price > 0`).
    - `src/lib/mock-schedule.ts` (+ тесты, 11 штук) — чистые функции `getMockEntryState`/`areMockResultsPending`, зеркалящие SQL-логику для UI (каталог мока показывает «Откроется {дата}» / «Время истекло» вместо кнопки «Начать»; экран результата показывает окно ожидания вместо баллов).
    - **Осознанный компромисс:** список `/results` тоже скрывает балл до даты публикации, но это не криптографически защищено — `fetchUserMockResults` всё ещё получает сырые числа с сервера, скрытие происходит на уровне рендера. Настоящая защита (сервер физически не отдаёт балл) реализована только в самый чувствительный момент — сразу после сдачи, в ответе `submit_mock`. Технически подкованный ученик, открыв вкладку "Сеть" на `/results`, теоретически может увидеть число раньше срока — риск сочли приемлемым (это не выпускной экзамен с проктором, а лишь чтобы результаты не разлетелись по группе в чате раньше времени для большинства пользователей).
    - Обратная совместимость: у всех существующих платных моков `starts_at IS NULL` → работают ровно как раньше, без каких-либо ограничений.
