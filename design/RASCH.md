# Rasch Measurement System — единственный источник правды

Всё про измерение уровня ученика — здесь. Логика раньше была размазана по
`src/lib/rasch.ts`, `certificate-scale.ts`, `native-cert.ts`,
`mock-grade-level.ts`, `english-cefr.ts` и роуту пересчёта, а решения — по
`design/FIX.md` и `CLAUDE.md`. Прежде чем трогать баллы, читай этот файл.

Норма — спецификация **Rasch Measurement System 2.0** владельца (216 пунктов);
ссылки вида §66 ведут в неё. Цель платформы — Миллий сертификат: считать так
же, как Агентство по оценке знаний.

## 1. Модель

Одна шкала для способности ученика и сложности задания. Для дихотомического
задания (§1):

```
P(X=1 | θ, b) = 1 / (1 + e^-(θ-b))
```

`θ` — способность, `b` — сложность, обе в логитах. Смысл разницы (§2):

| θ − b | P(верно) |
|---|---|
| +2 | ≈ 88% |
| +1 | ≈ 73% |
| 0 | 50% |
| −1 | ≈ 27% |
| −2 | ≈ 12% |

Логит — логарифм отношения шансов, `ln(P/(1−P))` (§3). **Сложность задания —
это не количество баллов** (§14), а положение на шкале.

Что из этого следует и постоянно забывается:

- балл в процентах — **не** способность (§13). Процент отвечает «сколько
  заданий этого теста решено», Rasch — «какой уровень объясняет ответы с учётом
  сложности»;
- `θ` **не** равна сумме или среднему сложностей решённых заданий (§157–158);
- задание информативнее всего, когда `θ ≈ b` (§27): именно там модель различает
  близкие уровни. Слишком лёгкое и слишком сложное дают почти ноль информации.

## 3. Главная проблема: показанный балл не измеряет уровень

Измерено на проде, не предположение. Замер от 2026-09-08, 90 работ с баллом
(данные живые, абсолютные числа могли уйти — воспроизводится запросами из §8):

```
Mock Matematika    55 заданий   mean(b) = 0.0000000000   mean(θ) = −1.836   ср. балл = 66.67
Ona Tili           49 заданий   mean(b) = 0.0000000000   mean(θ) = −1.090   ср. балл = 33.34
```

Складываются две вещи:

1. **Каждый тест центрирует свою шкалу сам.** `mean(b)` — ноль до десятого
   знака в обоих тестах, то есть у каждого свой произвольный нуль. §66
   предупреждает прямо: без linking две независимые калибровки несопоставимы.
2. **Балл — Z-стандартизация по когорте того же теста** (`raschThetaToT`).
   Поэтому средний T всегда ровно 50, а средний показанный балл — всегда 66.67
   из 100.

Следствия:

- по математике когорта решила ≈23% заданий и оказалась заметно ниже своего
  пула (θ = −1.84), а средний балл — **66.67**. Когорта, решившая 5%, получила
  бы **те же 66.67**;
- **прогресс между месяцами измерить нельзя** (§12, §130–131) — ровно то, ради
  чего Rasch и берут;
- сильная когорта **понижает** балл каждого: число говорит о месте внутри
  теста, а выглядит как абсолютный уровень.

Расхождение с §112–115: преобразование θ → балл должно быть фиксированным и
версионированным, а не зависеть от того, кто ещё сдавал.

## 5. Решения владельца — не менять, не обсудив

Зафиксированы явно; каждое ограничивает то, что можно делать с моделью.

- **Итоговый балл: 100 у общеобразовательных, 75 у иностранных языков.**
  T-шкала (0–75) — величина промежуточная; перевод в шкалу предмета —
  [certificate-scale.ts](../src/lib/certificate-scale.ts).
- **Уровень A+..C — по ближайшему целому T** («ближе к 65 — значит уровень
  65»). Пороги 70/65/60/55/50/46 заданы на T-шкале, не на сотенной.
- **Балл показывается с одной десятой.** Единственное округление —
  `roundScore`; промежуточные шаги считают точно.
- **Сумма баллов за задания свободная.** Прежние `normalizePointsTo75` и гейт
  «сумма = 75» сняты специально: сложность учитывает сама модель
  (`design/FIX.md`, «Две шкалы 75»). **Приводить сумму к 100 нельзя** — это
  вернуло бы самодельную шкалу.
- **Родной язык — два раздела.** Тест по Рашу плюс сочинение по 24-балльному
  критерию, переведённое таблицей, итог — среднее арифметическое
  ([native-cert.ts](../src/lib/native-cert.ts)). Отсюда «половина балла» у тех,
  кто сочинение не написал.
- **Средние — простым средним по работам**, как у групп и учителей.
- **Placement/Diagnostic никому не показывает разбор по вопросам**, даже
  админу, — только итоговый процент.
- **Проценты остаются только у вступительных тестов**; у моков везде баллы.

## 6. Порядок правок

Каждый этап опирается на предыдущий.

- **Этап 0 — этот документ.** Готово.
- **Этап 1 — балл перестаёт зависеть от когорты.** Фиксированное
  преобразование θ → балл вместо Z по когорте. Даёт абсолютность **внутри
  теста**; сопоставимость между формами закрывает этап 4. Меняет **все уже
  выставленные баллы** — нужно решение: пересчитывать прошлое или фиксировать
  шкалу начиная с новых тестов.
- **Этап 2 — точность.** SE у θ и b, информация теста, сохранение
  `converged`/`iterations`, статус качества у результата. Без этого нельзя ни
  честно ранжировать (§81), ни отличить надёжный балл от шумного.
- **Этап 3 — версионирование.** Версии калибровки, ссылка из результата, запись
  estimator-а. Результат становится воспроизводимым (§189), пересчёт — без
  потери истории.
- **Этап 4 — банк и якоря.** Общий банк, якоря в месячных формах, linking к
  постоянной шкале. Только после этого «прогресс за месяц» — настоящая
  величина.
- **Этап 5 — диагностика.** Infit/Outfit, DIF по филиалам, локальная
  зависимость через существующий `group_key`, размерность. Сначала обнаружение и
  флаги; **удаление заданий — никогда автоматически** (§40, §56).
- **Этап 6 — пропуски.** Явные OMITTED и NOT_REACHED вместо нынешнего
  «неотвеченное = неверное».
- **Этап 7 — позже.** PCM, MFRM для проверяющих, vertical scaling, MST.

## 7. Дополнения к спецификации

Тем ниже в спецификации 2.0 нет. Взяты не для полноты — у каждой есть
применение именно здесь.

### 7.1 WLE (Warm, 1989) — формула

§165 и §171 требуют выбрать один operational estimator, но без формулы это не
реализовать. У MLE на конечных тестах есть смещение к краям шкалы, и именно оно
делает крайние оценки бесконечными (§22–23). Warm добавляет к уравнению
правдоподобия поправочный член:

```
∂/∂θ [ ln L(θ) ] + J(θ) / (2 I(θ)) = 0

I(θ) = Σ Pᵢ(1−Pᵢ)                 — информация теста
J(θ) = Σ Pᵢ(1−Pᵢ)(1−2Pᵢ)          — третий момент
```

Для чистого Rasch это раскрывается в:

```
Σ (xᵢ − Pᵢ) + J(θ) / (2 I(θ)) = 0
SE_WLE(θ) ≈ 1 / √I(θ)
```

Главное свойство: WLE даёт **конечную** оценку и при 0 верных, и при всех
верных — то есть закрывает §22–25 без выдуманных «+3» (§25). Это и есть
кандидат в operational estimator этапов 1–2, вместо нынешней поправки 0.3 к
сырому баллу.

### 7.2 Механизм пропусков: MCAR / MAR / MNAR

Прямо про наши 683 неотвеченных ответа. Спецификация даёт статусы (§92–93), но
не теорию, а от механизма зависит, искажает ли политика оценку.

- **MCAR** — пропуск не связан ни с чем. Выбросить ответ безопасно.
- **MAR** — пропуск связан с наблюдаемым (например, дошёл до конца или нет).
  Безопасно, если условие учтено.
- **MNAR** — пропуск связан с самим ненаблюдаемым ответом: ученик молчит
  **потому что** не знает. Выбросить — завысить θ; считать неверным — занизить
  у того, кто не дошёл.

Практический вывод для платформы: пропуски в середине работы («не знаю») и
пропуски в хвосте («не успел») — разные механизмы, и одна политика на оба
неверна в любом случае. Отсюда этап 6: сначала различить OMITTED и
NOT_REACHED, потом выбрать политику для каждого и записать её в версию.

### 7.3 MFRM с фасетом «проверяющий»

Самое недооценённое. У нас **уже** люди вручную оценивают сочинения
(`mock_reviewers`), а строгость у людей разная — и она попадает прямо в балл за
родной язык, где сочинение весит половину. Многофасетная модель добавляет
фасет:

```
ln(Pₙᵢⱼₖ / Pₙᵢⱼ₍ₖ₋₁₎) = θₙ − bᵢ − cⱼ − τₖ
```

где `cⱼ` — строгость проверяющего `j`, `τₖ` — порог категории. Позволяет
отделить «ученик слабее» от «проверяющий строже» и вычесть вторую из балла.
Пока проверяющих единицы, `cⱼ` оценить не на чем — но фиксировать, **кто**
проверял, нужно с самого начала, иначе задним числом уже не разделить. Это
пишется в `mock_answer_details.reviewed_by` и там уже есть.

### 7.4 Vertical scaling

Центр учит разные классы, и сравнивать 9-й с 11-м на одной шкале «просто
потому, что оба в логитах» нельзя (§118). Вертикальное шкалирование связывает
уровни через общие задания, взятые с перекрытием: часть заданий 10-го класса
даётся и девятому, и одиннадцатому. Технически это тот же linking из §65–69, но
между **уровнями обучения**, а не между месяцами. Нужно, когда появится
сквозной рейтинг по всему центру.

### 7.5 MST — многоступенчатый тест

Реалистичнее CAT (§198–201) для платформы, где тест приходит из PDF целой
формой: адаптивность на уровне **модулей**, а не отдельных заданий.

```
Модуль-маршрутизатор (средняя сложность)
        ↓ оценили θ
   ┌────┴────┐
лёгкий    сложный        ← второй этап выбирается по θ
```

Плюсы против CAT: формы собираются и проверяются заранее, содержание
контролируемо, exposure предсказуем, работает без пересчёта после каждого
ответа. Требует того же, что и CAT: калиброванного банка с известными `b` —
поэтому только после этапа 4.

### 7.6 Чего сознательно нет

- **2PL / 3PL** — спецификация прямо запрещает подмену модели (§152–154).
  Дискриминация в Rasch фиксирована; оценивать её отдельно значит перестать
  быть Rasch и потерять инвариантность, ради которой всё и строится.
- **Saltus, hybrid Rasch** — нет сценария.
- **Multidimensional CAT** — нет ни банка, ни CAT; обсуждать рано.
- **Kolmogorov–Smirnov, Cressie** — экзотические тесты соответствия до того,
  как появились Infit/Outfit, это порядок наоборот.
- **Generalizability theory** — другая система координат; для нашей задачи
  (разделить ученика и проверяющего) её роль закрывает MFRM.
- **LPCM, автогенерация заданий** — на будущее: частичных баллов в данных
  сегодня нет, а задания и так извлекаются из PDF распознаванием.

## 8. Запросы для проверки

Ими получены числа из §3 и §4; ими же проверяется, что правки подействовали.

```sql
-- §3. Каждый тест центрирует шкалу сам: mean_b — ноль до десятого знака.
-- После перехода на общую шкалу (этап 4) он обязан перестать быть нулём.
select mt.title, count(ic.id) as items,
       round(avg(ic.difficulty)::numeric, 10) as mean_b,
       (select round(avg(mr.rasch_score)::numeric,3) from mock_results mr where mr.mock_test_id = mt.id) as mean_theta,
       (select round(avg(mr.level_score)::numeric,2) from mock_results mr where mr.mock_test_id = mt.id) as mean_score
from mock_item_calibration ic join mock_tests mt on mt.id = ic.mock_test_id
group by mt.id, mt.title;

-- §3. Средний балл — константа 66.67 при любой подготовке когорты.
-- После этапа 1 обязан начать зависеть от того, как решали.
select mt.subject_id,
       sum(mr.correct_answers) || '/' || sum(mr.total_questions) as correct_of_asked,
       round(100.0*sum(mr.correct_answers)/nullif(sum(mr.total_questions),0),1) as pct_correct,
       round(avg(mr.level_score),2) as mean_score
from mock_results mr join mock_tests mt on mt.id = mr.mock_test_id
group by mt.subject_id;

-- §4 п.4. Доля неотвеченного, которое уходит в модель как неверное.
select q.question_type, count(*) as answers,
       count(*) filter (where ad.selected_answer = 'null' or ad.selected_answer is null) as unanswered
from mock_answer_details ad join mock_questions q on q.id = ad.question_id
group by q.question_type order by answers desc;

-- §4 п.5. Testlet-группы, которые модель считает независимыми заданиями.
select mt.title, q.group_key, count(*) as items_in_group
from mock_questions q
join mock_sections s on s.id = q.section_id
join mock_tests mt on mt.id = s.mock_test_id
where q.group_key is not null
group by mt.title, q.group_key having count(*) > 1 order by items_in_group desc;

-- §4 п.12. Есть ли вообще частичные баллы (сегодня 0 — политомность не срочна).
select count(*) as genuinely_partial from mock_answer_details
where coalesce(points_earned,0) > 0 and max_points is not null and points_earned < max_points;
```

## 9. Что важно помнить

Rasch не спрашивает «сколько баллов дать этому вопросу» и не спрашивает
«сколько процентов набрал ученик». Он спрашивает: **какой уровень способности
лучше всего объясняет именно этот набор ответов на задания известной
сложности** (§216).

Поэтому:

- **`θ` — оценка, а не истина** (§208). У неё есть SE, и без него сравнение двух
  учеников не имеет смысла (§81).
- **Инвариантность не даётся бесплатно** (§11, §210–211). Она следствие
  хорошего соответствия модели, и её нужно проверять, а не предполагать.
- **Misfit ≠ «удалить задание»** (§40). Сначала обнаружить, потом исследовать
  причину, потом решать — и решать человеку.
- **Ranking и pass/fail — слой отчётности поверх измерения** (§117, §205), а не
  часть модели.
- **Нельзя сравнивать θ по математике с θ по английскому** только потому, что
  обе в логитах (§118–120): единица одна, конструкт разный.
