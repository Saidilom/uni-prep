## ДЕЙСТВУЮЩИЙ РАСЧЁТ на 2026-09-11 — читать раньше остального

Решением владельца расчёт переведён на его документ «Что делать на платформе —
шаг за шагом». Две вещи ниже **отменяют** то, что написано про них дальше по
этому файлу (§268 и модуль E) — дальше оставлено как история, а не как норма.

**1. Сложность задания — из доли решивших**, а не из совместной калибровки:

```
β = −ln( p / (1 − p) ),  p — доля верных среди ОТВЕЧАВШИХ (пропуски вне, §A.3)
```

Крайние доли (`p = 0` или `p = 1`) сдвигаются на 0,3 внутрь: без этого 5 заданий
из 55 на боевом моке дают `+Infinity` и обрывают расчёт. Код —
`src/lib/rasch-proportion.ts`, метод помечен в данных
(`mock_item_calibration.difficulty_method = 'PROPORTION'`).

JMLE (`estimateRasch` в `rasch.ts`) остаётся в репозитории и под тестами, но в
расчёте балла НЕ участвует.

**2. Z-стандартизация — по ПОТОКУ, а не по эталонной популяции:**

```
μ, σ — среднее и выборочное отклонение θ сдавших ЭТОТ тест
Z = (θ − μ) / σ        T = 50 + 10·Z
```

Отсюда следует, и это принято сознательно: **средний T любого теста равен ровно
50 при любой подготовке**. Балл означает место в своей группе, а не уровень.
Сравнивать им месяцы между собой нельзя.

Статистика потока **закрепляется за тестом** (`mock_tests.cohort_mu`,
`cohort_sigma`, `cohort_n`, `cohort_frozen_at`), как только результат показан
хотя бы одному ученику. Без заморозки каждая новая сдача двигала бы баллы всем
остальным: роут пересчитывает весь тест после каждой отправки.

Поток без разброса (один сдавший; все ответили одинаково) балла НЕ даёт:
`σ` пуста, `level_score` пуст, `measurement_status = INSUFFICIENT_INFORMATION`.
Подставлять туда эталон запрещено (§233).

**Что это стоило.** Пересчитаны все 90 показанных работ, создано 90 ревизий
(`reason = cohort_centering_proportion_difficulty`). Букву сменили 28 работ, все
по математике: средний балл там 32,89 → 50,00, сертификат (C и выше) получили 28
вместо 3. У «Ona Tili» буква не изменилась ни у кого — балл вырос с 19,80 до
25,00, но итог там делится пополам с непроверенным сочинением и до порога C (46)
не доходит.

# ТЗ: Психометрический движок Rasch под Milliy sertifikat
### Версия 1.0 · Целевой эталон — методика BMA (Bilim va malakalarni baholash agentligi)

---

## 0. Назначение и границы

### 0.1. Что строим
Измерительный движок (measurement engine), а не калькулятор баллов. Он обязан по ответам ученика выдать: способность θ, её погрешность SE, диагностику качества и балл по 75-балльной шкале с уровнем A+…C — так, чтобы результат совпадал с реальным Milliy sertifikat от BMA.

### 0.2. Ключевой принцип
Система НЕ работает по цепочке `кол-во правильных → процент → балл → оценка`.
Система работает по цепочке:

```
ответы
  → сырое оценивание (scoring, с частичным кредитом где есть)
  → калиброванные параметры заданий (b_i)
  → модель вероятности Раша P(θ,b)
  → оценка параметра θ (WLE)
  → SE
  → диагностика качества (fit / DIF / Q3 / PCA)
  → выравнивание вариантов (equating)
  → трансформация в шкалу 0–75
  → уровень A+…C
```

Каждое число обязано иметь математическое происхождение. Никаких «магических коэффициентов».

### 0.3. Эталонные параметры BMA (жёстко зашить)
- Модель: **Rasch (1PL)** для закрытых заданий, **PCM** для открытых заданий с частичным кредитом.
- Тип теста: **линейный фиксированный** (не адаптивный).
- Шкала отчётного балла: **0–75** (максимум 75, не 100).
- Пороги уровней (на шкале 75):

| Балл | Уровень | Примечание |
|---|---|---|
| > 70 | A+ | при поступлении — максимальный балл по предмету |
| 65 – 69.9 | A | при поступлении — максимальный балл по предмету |
| 60 – 64.9 | B+ | пропорциональный балл |
| 55 – 59.9 | B | пропорциональный балл |
| 50 – 54.9 | C+ | пропорциональный балл |
| 46 – 49.9 | C | пропорциональный балл |
| < 46 | нет сертификата | — |

- У каждого предмета — своя независимая шкала. Сравнение θ между предметами запрещено.
- Ветки языка теста: **uz / ru** — обязательная проверка на DIF.
- Срок действия результата (у BMA): 3 года (для нашей платформы — метаданные результата).

### 0.4. Что вне движка
Убраны: весь CAT, LLTM, MDRM, Mixed Rasch, 2PL/3PL, bookmark. См. файл `1_UBRANO_ne_nuzhno.md`.

## 1. Модель данных (объекты и связи)

### 1.1. Базовые объекты

**Person (ученик)**
- `person_id`
- `θ` — оценка способности (логиты)
- `SE(θ)` — стандартная ошибка
- `raw_score` — сырой балл
- `responses[]` — набор ответов
- `quality_status` — TRUSTED / FLAGGED / INVALID
- `fit`: infit, outfit персоны

**Item (задание)**
- `item_id`, `item_version_id`
- `type`: BINARY | POLYTOMOUS(PCM)
- `b_i` — калиброванная сложность (логиты); для PCM — вектор порогов `τ_ik`
- `SE(b_i)`
- `raw_points` — сколько сырых баллов даёт (1 для бинарного; для открытого — по спецификации, напр. 3.2)
- `branch`: uz | ru
- `content_area` — тема/раздел
- `status`: FIELD_TEST | ACTIVE | RETIRED | INVALID
- `calibration_version_id`
- `fit`: infit, outfit; point-measure correlation

**Response (ответ)**
- `person_id`, `item_id`, `item_version_id`
- `X` — сырой результат: для бинарного {0,1}; для PCM {0,1,…,m}
- `state`: CORRECT | INCORRECT | OMITTED | NOT_REACHED | TECHNICAL_FAILURE | INVALIDATED
- `response_time` (хранить, не моделировать)

**Calibration (снимок калибровки)**
- `calibration_version_id`
- `estimator`: JMLE | MMLE | CML | PAIRWISE + версия
- `data_snapshot_id` — какие данные использованы
- `items[]` с их `b_i`, `SE`
- `status`: DRAFT | APPROVED | REJECTED
- **иммутабелен** после утверждения

**Scale / Equating**
- `scale_id` (на предмет)
- `linking_transform`: A, B (в `S = A·θ + B`)
- `anchor_set[]`
- `equating_uncertainty`

### 1.2. Мастер-связь (что от чего зависит)
```
Response → Scoring → (valid) → Calibration(b_i) → Rasch P(θ,b) → θ_estimation → SE
   → Quality(fit/DIF/Q3/PCA) → Equating(anchors) → Scale(A,B) → Report(75) → Level(A+…C)
```
Разрыв любой связи = результат недоверенный. Движок обязан всегда знать: `θ, b, P(θ,b), SE(θ), Fit`.

### 1.3. Что нельзя терять никогда
`calibration_version`, `estimator_version`, `scale_transform (A,B)`, `anchor_set`, `data_snapshot`, `cut_scores`, все исключения (с причиной). Всё версионируется и аудируется.

## 2. Модуль A — Сырое оценивание (Scoring before Rasch)

### A.1. Бинарный ответ (разделы 2)
`X_ni ∈ {0,1}`, 1 = верно, 0 = неверно.
Пропущенный ответ **не** превращать автоматически в 0 при калибровке — см. A.3.

### A.2. Частичный кредит (раздел 72, 79)
Открытые задания дают дробные сырые баллы по спецификации предмета. Пример (математика, части a/b):
- только a верно → 1.5
- только b верно → 1.7
- a и b верно → 3.2
- ничего → 0

Для движка Раша такой пункт кодируется как PCM-задание с упорядоченными категориями. Сырые баллы (1.5/1.7/3.2) — это отчётные весa; в PCM работаем с категориями 0,1,2,…, а веса применяются на уровне raw_score.

### A.3. Статусы ответов (раздел 73)
`CORRECT / INCORRECT / OMITTED / NOT_REACHED / TECHNICAL_FAILURE / INVALIDATED`.
- **При калибровке заданий:** OMITTED и NOT_REACHED — это missing, а не 0. Не кормить их в likelihood как 0.
- **При выдаче балла ученику (режим экзамена):** применять политику BMA — пропуск не даёт баллов (эквивалент 0 для сырого балла), но это политика оценивания, а не свойство модели. Прописать явным флагом `missing_policy = EXAM | CALIBRATION`.

### A.4. NOT_REACHED (раздел 74)
Если ученик не дошёл до задания из-за времени — не превращать в неверный, если спецификация теста определяет его как not reached. Хранить отдельно от INCORRECT.

**Что хранить:** сырой X, state, raw_points, применённую missing_policy.

## 3. Модуль B — Модель Раша: вероятность и логит

### B.1. Два латентных параметра (раздел 1)
`θ_n` — способность ученика n. `b_i` — сложность задания i. Оба на одной логит-шкале.

### B.2. Основная формула (раздел 3)
```
P_ni = exp(θ_n − b_i) / (1 + exp(θ_n − b_i))
     = 1 / (1 + exp(−(θ_n − b_i)))
```

### B.3. Интерпретация θ−b (раздел 4)
- θ = b → P = 0.5
- θ−b = 1 → P ≈ 0.73
- θ−b = 2 → P ≈ 0.88
- θ−b = −1 → P ≈ 0.27

### B.4. Logit (раздел 5)
```
logit(P) = ln[P / (1−P)]
logit(P_ni) = θ_n − b_i
```
Logit — не процент и не балл. Это единица измерения на общей шкале.

### B.5. Идентификация шкалы (раздел 6)
Логит-шкала не имеет абсолютного нуля. Нуль задаётся ограничением (constraint): обычно `mean(b_i) = 0` по набору калибровки. Зафиксировать и хранить конвенцию — иначе θ несопоставимы между калибровками.

### B.6. Raw score person / item (разделы 7, 9)
Сырой балл персоны = Σ X по заданиям. Сырой балл задания = Σ X по персонам. В Раше при полных данных **сырой балл — достаточная статистика для θ**: одинаковый сырой балл → одинаковый θ (на одном варианте).

### B.7. Почему одинаковый процент ≠ одинаковый θ (раздел 8)
Два ученика с 60% верных могут иметь разный θ, если решали разные по сложности задания. Именно поэтому нельзя «процент → балл». Это обоснование самой модели — оставить в спеке как объяснение для методистов.

### B.8. Likelihood, score function, expected score, monotonicity (10–13)
- Likelihood персоны: `L(θ) = Π P_i^{x_i} (1−P_i)^{1−x_i}`
- Score function (первая производная log-L): `U(θ) = Σ (x_i − P_i)`
- Expected score: `E = Σ P_i`
- Monotonicity: P растёт по θ монотонно → единственный максимум likelihood (для не-экстремальных баллов).

**Что хранить:** формула и константа идентификации шкалы, версия модели (RASCH_BINARY / RASCH_PCM).

## 4. Модуль C — Оценка θ (person estimation)

### C.1. Итерационная процедура (разделы 14, 15)
Ньютон-Рафсон / Fisher scoring:
```
1. Взять valid responses.
2. Взять калиброванные b_i.
3. Выбрать стартовую θ.
4. Для каждого item вычислить P_i.
5. Вычислить U(θ) = Σ(x_i − P_i).
6. Вычислить I(θ) = Σ P_i(1−P_i).
7. Обновить: θ_{t+1} = θ_t + U(θ)/I(θ)   (для MLE)
8. Проверить сходимость.
9. Нет сходимости — повторить.
10. Достигнут max_iter → статус NON_CONVERGED.
11. После сходимости — θ.
12. Вычислить SE.
13. Прогнать диагностику качества.
```

### C.2. Стартовая θ (раздел 16)
`θ_0 = ln(r / (L − r))`, где r — сырой балл, L — число заданий (PROX-приближение). Или 0. Версионировать конфигурацию.

### C.3. Сходимость (раздел 17)
Критерий: `|θ_{t+1} − θ_t| < ε` (напр. ε = 0.0001) И/ИЛИ `|U(θ)| < δ`. Зафиксировать ε и δ.

### C.4. Max iterations (раздел 18)
Верхний предел (напр. 100). При недостижении — статус NON_CONVERGED, не выдавать «тихий» результат.

### C.5. Экстремальный балл (раздел 19)
Сырой балл 0 или максимум → MLE даёт ±∞. **Нельзя** заменять ∞ на 10 или любое число вручную.

### C.6. Конечная оценка (раздел 20)
Для экстремальных баллов применять явно выбранный метод: **WLE** (рекомендуется), либо MAP/EAP. Метод фиксируется в конфигурации, а не выбирается «на лету».

### C.7. MLE (раздел 21)
`θ̂_MLE = argmax_θ L(θ)`. Плюс: без prior. Минус: экстремальные баллы → ∞.

### C.8. WLE — основной estimator θ ученика (раздел 22)
Weighted Likelihood Estimation (Warm, 1989) убирает смещение MLE и даёт конечную θ для 0 и 100%.
```
U_W(θ) = Σ(x_i − P_i) + J(θ) / (2·I(θ))
I(θ) = Σ P_i(1−P_i)
J(θ) = Σ P_i(1−P_i)(1−2P_i)
Решать U_W(θ) = 0 методом Ньютона.
SE(θ) ≈ 1 / √I(θ̂)
```
WLE — отдельная версия estimator’а. Нельзя выдавать результат WLE под именем MLE или с их одинаковым числом.

### C.9. MAP / EAP / prior (разделы 23–25) — ПОД УСЛОВИЕМ
Только если решите использовать байесовскую оценку вместо WLE.
- `θ̂_MAP = argmax_θ [ln L(θ) + ln g(θ)]`
- `θ̂_EAP = ∫θ L(θ)g(θ)dθ / ∫L(θ)g(θ)dθ`
При использовании хранить: тип распределения prior, mean, variance, SD, версию prior. Смена prior = новая версия estimator’а.

**Что хранить:** estimator (WLE) + версию, ε/δ/max_iter, статус сходимости, θ, SE.

## 5. Модуль D — Информация и стандартная ошибка

### D.1. Item information (раздел 26)
Для бинарного Раша: `I_i(θ) = P_i(1 − P_i)`. Максимальна при θ = b_i (тогда = 0.25).

### D.2. Максимум item information (раздел 27)
Задание даёт больше всего информации, когда его сложность совпадает со способностью ученика. Это основа таргетирования вариантов.

### D.3. Test information (раздел 28)
`I(θ) = Σ_i I_i(θ)`. Сумма по всем заданиям варианта. Кривая TIF показывает, где тест точен.

### D.4. Standard error (раздел 29)
`SE(θ) = 1 / √I(θ)`. Чем больше информация — тем меньше ошибка.

### D.5. Information ≠ SE (раздел 30)
Информация аддитивна по заданиям; SE — нет. Хранить обе, не путать.

### D.6. Observed information (раздел 31)
Наблюдаемая информация = вторая производная log-likelihood со знаком минус. Для Раша совпадает с Fisher information ΣP(1−P). Использовать для SE при не-стандартных estimator’ах.

### D.7. Доверительный интервал (раздел 32)
`θ ± z·SE(θ)` (z = 1.96 для 95%). После перевода в шкалу 75 → `S ± A·z·SE`. Это то самое ±SE в баллах для отчёта ученику.

### D.8. Разница двух измерений (раздел 33)
`SE(θ1 − θ2) = √(SE(θ1)² + SE(θ2)²)`. Нужна, чтобы сказать «различие значимо» (напр. между двумя попытками или двумя вариантами).

### D.9. Item targeting (раздел 34)
Вариант должен быть нацелен на диапазон способностей популяции: пик TIF около среднего θ выпускников, покрытие у порогов A+…C. При сборке проверять.

### D.10. Person-item map / карта Райта (раздел 35)
Общая логит-ось: слева — распределение θ учеников, справа — b заданий. BMA её строит. Реализовать визуализацию — методистам понятна с одного взгляда.

### D.11. Test Characteristic Curve (раздел 36)
`TCC(θ) = Σ_i P_i(θ)` — ожидаемый сырой балл как функция θ. Основа таблицы raw→θ.

### D.12. ICC (раздел 37)
Item Characteristic Curve — P_i как функция θ. BMA использует для анализа заданий. Строить для каждого задания.

**Что хранить:** TIF варианта, SE каждого θ, ДИ, TCC-таблицу варианта.

**СДЕЛАНО (D.3, D.9–D.12).** `src/lib/rasch-curves.ts`, отрисовка —
`src/components/psychometric-charts.tsx`.

## 6. Модуль E — Калибровка заданий (item calibration)

### E.1. Выбор estimator калибровки (разделы 103–108)
Калибруем b_i отдельно от оценки θ ученика. Кандидаты:
- **CML (Conditional MLE, раздел 103)** — условная по сырому баллу; даёт несмещённые b, не зависит от распределения θ. Хорош для Раша.
- **JMLE (раздел 104)** — совместная оценка θ и b (стандарт Winsteps). Проста, но даёт лёгкое смещение b на коротких тестах → нужна поправка `(L−1)/L`.
- **MMLE (раздел 105)** + **EM (106)** — маргинальная, интегрирует θ по популяционному распределению.
- PAIRWISE (108) — альтернатива, ПОД УСЛОВИЕМ.

**Решение:** зафиксировать ОДИН estimator (рекоменд. CML или MMLE), версионировать. Не смешивать.

### E.2. Сходимость likelihood (раздел 107)
Критерий сходимости по изменению log-likelihood и по параметрам. Фиксировать порог.

### E.3. Версионирование estimator’а (раздел 109)
Любая калибровка помечена `estimator + version`. Смена метода/настроек → новая версия.

### E.4. Снимок данных калибровки (раздел 110)
`data_snapshot_id`: точный набор ответов, на которых получены b. Иммутабелен.

### E.5. Eligibility данных (раздел 111)
В калибровку берём только валидные ответы валидных персон (см. модуль N). Мошенники, тех.сбои, invalidated — исключаются с записью причины.

### E.6. Contamination (раздел 112)
Загрязнённые данные (утечка заданий, аномальные паттерны) не должны попадать в калибровку. Проверять до расчёта b.

### E.7. Точность и стабильность калибровки (разделы 164, 167, 168)
- Точность: SE(b_i) в допуске.
- Стабильность: b не должна скакать между близкими снимками.
- Стабильность параметров: сравнение b_new vs b_old (см. дрейф, модуль I).

### E.8. Размер выборки (раздел 166)
Единого «магического N» нет. Зависит от модели, разброса сложности, категорий, DIF, точности. **Практический ориентир: ≥ 250–300 валидных ответов на задание** для стабильной b с SE ≈ 0.12–0.15 логита. Для PCM-заданий — больше (нужны наблюдения в каждой категории).

### E.9. Экстремальный балл задания (раздел 165)
Задание, на которое все ответили верно/неверно → b не оценивается (±∞). Не калибровать, помечать, исключать из активного набора до накопления вариативности.

### E.10. SE, Hessian, ковариация (разделы 175–177)
- `SE(b_i)` из обратной информационной матрицы.
- Hessian — матрица вторых производных log-L; её обращение даёт ковариацию.
- Covariance matrix — для корректных SE и сравнений.

### E.11. Sparse matrix / связность банка (разделы 162, 163)
Матрица «персоны × задания» разрежена (не все решают всё). Калибровка возможна только при достаточной **связности**: задания должны быть связаны общими персонами/якорями. Проверять граф связности до калибровки.

**Что хранить:** estimator+версия, data_snapshot, b_i, SE(b_i), ковариацию, граф связности, лог исключений.

## 7. Модуль F — Fit-диагностика

### F.1. Общее определение fit (раздел 38)
Fit — насколько наблюдаемые ответы согласуются с ожиданиями модели. Плохой fit = задание/персона ведут себя не по Рашу.

### F.2. Expected variance (раздел 39)
`V_ni = P_ni(1 − P_ni)` — дисперсия бинарного ответа по модели.

### F.3. Стандартизованный остаток (раздел 40)
```
z_ni = (X_ni − P_ni) / √V_ni
```

### F.4. Outfit MNSQ (раздел 41)
```
Outfit = (1/N) Σ z_ni²
```
Чувствителен к выбросам (неожиданные ответы на очень лёгкие/трудные задания).

### F.5. Infit MNSQ (раздел 42)
```
Infit = Σ (X_ni − P_ni)² / Σ V_ni
```
Взвешен информацией → чувствителен к «внутренним» несоответствиям, устойчив к выбросам.

### F.6. Откуда берутся Infit/Outfit (раздел 43)
Процедура: для каждого observation считаем P, V=P(1−P), residual=X−P, z=residual/√V; z² → в Outfit; residual² и V → в Infit; после всех observations — MNSQ.

### F.7. Интерпретация MNSQ (раздел 44)
1.0 — идеальное соответствие. 1.20 ≈ на 20% больше вариации остатков, чем ждёт модель. Рабочий диапазон обычно **0.5–1.5** (для высоких ставок жёстче: 0.7–1.3).

### F.8. Overfit / Underfit (разделы 45, 46)
- Overfit (MNSQ < 1, напр. <0.5): ответы «слишком предсказуемы» — часто зависимость/дублирование.
- Underfit (MNSQ > 1, напр. >1.5): шум, угадывание, ошибки ключа, многомерность. Опаснее для измерения.

### F.9. ZSTD (раздел 47)
Стандартизованное t-значение MNSQ (через преобразование Wilson–Hilferty). Интерпретировать вместе с MNSQ: при больших выборках ZSTD раздувается — приоритет у MNSQ.

### F.10. Item fit vs Person fit (раздел 48)
Тот же аппарат применяется и к заданиям, и к персонам. Person misfit → флаг на аномальный паттерн (см. модуль N).

### F.11. Point-measure correlation (раздел 49)
Корреляция балла по заданию с общей мерой θ. Должна быть положительной; отрицательная/около нуля → ошибка ключа или дефект задания.

### F.12. Графический item fit (ДОБАВИТЬ, нет в файле)
Разбить учеников на 5–8 групп по θ; для каждой группы наблюдаемая доля верных vs модельная P(θ). График нагляднее Infit/Outfit и понятен без психометрической подготовки. Обязателен в отчёте по заданию.

**Что хранить:** infit, outfit, ZSTD, point-measure для каждого задания и персоны; данные для fit-графика.

## 8. Модуль G — Локальная независимость и размерность

### G.1. Local independence (раздел 50)
При фиксированном θ ответы на разные задания независимы. Нарушение → завышенная надёжность и смещённые b.

### G.2. Yen Q3 (разделы 51–53)
```
Q3(i,j) = corr(residual_i, residual_j)
```
Процедура: взять персон, ответивших на оба задания; взять остатки модели; посчитать корреляцию остатков; сравнить с эталонным уровнем; проверить содержательную/пассажную связь; выставить флаг зависимости.
Порог тревоги: обычно |Q3| выше базового уровня (≈ −1/(L−1)) на 0.2 и более. Зафиксировать порог.

### G.3. Dimensionality (раздел 56)
Раш предполагает одномерность (одна способность на предмет). Проверять, что тест меряет одно.

### G.4. Residual PCA (раздел 57)
PCA стандартизованных остатков. Если первый контраст имеет собственное значение (eigenvalue) ≥ ~2.0 и объясняет заметную долю дисперсии → подозрение на вторую размерность. Разбирать содержательно.

**Что хранить:** матрицу Q3-флагов, собственные значения контрастов PCA.

## 9. Модуль H — DIF (обязательный кейс uz / ru)

### H.1. DIF (раздел 60)
Differential Item Functioning: задание ведёт себя по-разному в группах при равном θ. **Для нас критично: одно задание на узбекском и русском может иметь разную сложность из-за перевода.**

### H.2. Оценка DIF (Rasch-based)
Откалибровать b задания раздельно в группах uz и ru (при заякоренной общей шкале):
```
DIF_i = b_i(focal) − b_i(reference)     [в логитах]
```

### H.3. SE и Z DIF (разделы 61, 62)
```
SE(DIF_i) = √(SE_focal² + SE_reference²)
Z_i = DIF_i / SE(DIF_i)
```
Флаг при |Z| > 2.0 (значимость).

### H.4. Effect size (раздел 63)
Значимость ≠ важность. Правило (в логитах): |DIF| < 0.43 — незначимо (A); 0.43–0.64 — умеренно (B); > 0.64 — сильно (C). Флаг «C» → задание на пересмотр перевода.

### H.5. Множественные сравнения (раздел 64)
При проверке многих заданий — поправка (Benjamini-Hochberg / Bonferroni), чтобы не ловить ложные DIF.

### H.6. DIF по branch (раздел 65)
Branch = язык теста (uz/ru). Обязательный отдельный прогон DIF по этой оси перед публикацией варианта.

**Что хранить:** DIF_i, Z, effect size, решение (оставить/переписать/убрать), для каждой пары групп.

## 10. Модуль I — Дрейф, версии, валидность заданий

### I.1. Item drift (разделы 66, 67)
Сложность задания меняется со временем (утечка, устаревание).
```
Δb_i = b_new − b_old
стандартизованный сдвиг = Δb_i / SE(Δb_i)
```
Проверять: абсолютное изменение, неопределённость, стандартизованный сдвиг, DIF, экспозицию, изменение контента.

### I.2. Invalid item (раздел 70)
Задание с ошибкой ключа/дефектом → статус INVALID, исключить из scoring и калибровки, зафиксировать причину.

### I.3. Item version (раздел 71)
Любое изменение задания (текст, ключ, перевод) → новая версия. Старая b не переносится на новую версию автоматически — рекалибровать.

### I.4. Item exposure / repeated item (разделы 68, 69) — ПОД УСЛОВИЕМ
Без CAT нет автоконтроля экспозиции, но как метрика безопасности банка (сколько раз задание показано, эффект повторной встречи) — полезно хранить.

**Что хранить:** историю b по версиям, Δb и сдвиг, статус, причины.

## 11. Модуль J — PCM (полиномиальные задания) — CORE

> Нужен обязательно: у BMA есть открытые задания с частичным кредитом (математика: части a/b).

### J.1. Rasch polytomous models (раздел 78)
Обобщение Раша на задания с >2 категориями баллов (0,1,…,m).

### J.2. Partial Credit Model (раздел 79)
Каждое задание имеет свои пороги переходов между категориями:
```
ln[ P_nik / P_ni,k-1 ] = θ_n − b_ik
```
где `b_ik` (τ_ik) — порог перехода из категории k−1 в k у задания i.
Вероятность категории k:
```
P_nik = exp(Σ_{j=0}^{k} (θ_n − b_ij)) / Σ_{h=0}^{m} exp(Σ_{j=0}^{h} (θ_n − b_ij))
```
(при b_i0 = 0).

### J.3. Rating Scale Model (разделы 80, 81, 185) — ПОД УСЛОВИЕМ
Частный случай PCM: общая структура порогов для группы заданий. Использовать только если задания делят единую шкалу категорий. PCM покрывает общий случай — по умолчанию PCM.

### J.4. Expected score / variance полиномиального (разделы 82, 83)
```
E_ni = Σ_k k · P_nik
V_ni = Σ_k (k − E_ni)² · P_nik
```
Эти E и V подставляются в те же residual/fit-формулы (модуль F).

### J.5. Category functioning (раздел 84)
Каждая категория должна «работать»: иметь наблюдения, быть наиболее вероятной на своём участке θ. Проверять кривые вероятностей категорий.

### J.6. Disordered thresholds (раздел 85)
Если пороги b_ik идут не по возрастанию θ (разупорядочены) → категория никогда не бывает модальной. Признак плохой категориальной структуры.

### J.7. Category collapsing (раздел 86)
При разупорядоченных/пустых категориях — объединять смежные категории (с записью решения). Не «тихо»: фиксировать как изменение (см. NO SILENT CATEGORY CHANGE).

### J.8. Category step estimation / expected category (разделы 180, 181)
Оценка порогов τ_ik в рамках калибровки; ожидаемая категория как функция θ.

### J.9. Polytomous information / fit / missing (разделы 182–184)
- Информация: `I_ni = V_ni` (дисперсия категорий).
- Fit: те же Infit/Outfit на базе E и V полиномиального.
- Missing в PCM обрабатывается как в модуле A (не 0 при калибровке).

**Что хранить:** τ_ik и SE, кривые категорий, решения о collapsing, model_type = RASCH_PCM.

## 12. Модуль K — Equating (выравнивание вариантов) — CORE

> Раш у BMA нужен прежде всего, чтобы разные варианты давали сопоставимый балл. Без этого «лёгкий» и «трудный» вариант дадут ученику разный результат при одной способности.

### K.1. Anchors (раздел 120)
Якорное задание связывает две калибровки/варианта. Хороший якорь: стабильный, репрезентативный, защищённый, информативный, без сильного DIF, без дрейфа, связан с обеими формами.

### K.2. Common-item linking (раздел 121)
Через общие задания находим преобразование сложностей формы B на шкалу формы A:
```
b_B(на общей шкале) = A · b_B + B
```
То же преобразование применяем к θ учеников формы B.

### K.3. Линейное преобразование шкалы (раздел 122)
`x' = A·x + B`. При A>0 сохраняет порядок и относительное расположение. В чистом Раше дискриминация постоянна → часто A=1 и линкинг сводится к сдвигу B; масштаб A вводят при mean-sigma (см. K.5).

### K.4. Mean-Mean linking (раздел 123)
A и B из средних сложностей общих якорей. Если разброс шкал различается — нужен масштабный коэффициент.

### K.5. Mean-Sigma linking (раздел 124)
Использует среднее И SD якорей:
```
A = SD_anchor(форма A) / SD_anchor(форма B)
B = mean_A − A · mean_B
```
Согласует и положение, и разброс.

### K.6. Anchor drift (раздел 125)
Для каждого якоря: `Δb_i = b_new − b_old`. Проверять абсолютное изменение, неопределённость, стандартизованный сдвиг, DIF, экспозицию, изменение контента.

### K.7. Robust anchor cleaning (раздел 126)
```
z_i = (Δb_i − median(Δb)) / MAD
```
Выброс НЕ равен автоматически плохому якорю — после статистического флага нужно расследование.

### K.8. Anchor removal (раздел 127)
Если якорь удалён — хранить: ID, причину, статистику, решение, версию калибровки.

### K.9. Equating uncertainty (раздел 128)
Итоговый балл несёт неопределённость от: калибровки, измерения якорей, самого линкинга. Хранить отдельно и учитывать в SE отчётного балла.

### K.10. No link without connectivity (раздел 129)
Если формы недостаточно связаны — НЕ выдавать искусственную общую шкалу. Вернуть `LINKING_NOT_IDENTIFIABLE`.

### K.11. Common-person design (раздел 130) — ОСНОВА ПРИВЯЗКИ К BMA
Линкинг можно строить через персон, прошедших несколько форм. **Это ваш механизм привязки к реальному Milliy sertifikat** (см. модуль R).

**Что хранить:** anchor_set, A и B на каждый линк, equating_uncertainty, лог очистки якорей.

## 13. Модуль L — Шкала и пороги (θ → 75 → уровень)

### L.1. Reporting transformation (раздел 136)
```
S = A_scale · θ + B_scale
```
Перевод логит-θ в отчётный балл. Трансформация версионируется. **A_scale, B_scale подбираются под шкалу 0–75 BMA** (см. модуль R — это не произвольные числа).

### L.2. Score ≠ θ (раздел 137)
θ = 0.73 может отображаться как балл 58 — только при утверждённой трансформации. Логит и балл не путать.

### L.3. Standard setting — применить, не выводить (разделы 131, 133, 225)
Пороги A+…C **заданы государством** (таблица в §0.3). Движок их применяет, не устанавливает. Стандарт-сеттинг не меняет θ — он лишь режет уже посчитанную шкалу.

### L.4. Cut score / уровни (разделы 133, 134)
6 уровней по границам: 46 / 50 / 55 / 60 / 65 / 70. Зашить как конфигурацию с версией и ссылкой на постановление.

### L.5. Cutscore uncertainty (раздел 135)
У границы уровня учитывать ошибку классификации: ученик с баллом 64.8 и SE в баллах ±1.5 мог бы быть B+. Показывать ДИ и, при необходимости, «пограничный» статус. Учитывать три источника: measurement error, panel variability (для нас — 0, пороги фиксированы), linking uncertainty.

### L.6. Subject scales / cross-subject (разделы 190, 191)
Каждый предмет — своя шкала (свои A_scale, B_scale). **Запрет** сравнивать θ математики и биологии напрямую и ранжировать по ним как по единой способности.

### L.7. Percentile / ranking (разделы 138, 139) — ПОД УСЛОВИЕМ
Для отчёта/рейтинга. Percentile требует reference-популяции: хранить группу, дату, методологию, версию. Ранжирование — только внутри одного предмета и общей шкалы.

### L.8. Reporting rounding (раздел 203)
Границы у BMA заданы до 0.1 (…64.9 / 65.0…). Правило округления отчётного балла зафиксировать явно (напр. до 0.1), чтобы у границ уровней не было расхождений с BMA.

**Что хранить:** A_scale, B_scale (на предмет) + версию, cut_scores + версию/ссылку на НПА, правило округления.

## 14. Модуль M — Field-test (пилотирование новых заданий)

### M.1. Field test items (раздел 159)

## 15. Модуль N — Качество: доверенная персона / задание / результат

### N.1. Person misfit (раздел 114)
Аномальный паттерн (лёгкие неверно, трудные верно) → высокий Outfit персоны. Флаг, не приговор.

### N.2. Cheating и Rasch (разделы 113, 174)
Раш сам по себе НЕ детектит списывание. Он даёт сигналы (misfit, аномалии), но не выносит вердикт. Прямо прописать это ограничение.
Дополнительно (нет в файле, добавить): person-level флаги — lz-индекс аномальности, аномально быстрые ответы, паттерн «трудные верно / лёгкие неверно». Только как флаг на просмотр.

### N.3. Quality status (раздел 115)
У персоны статус: TRUSTED / FLAGGED / INVALID. Только TRUSTED идут в калибровку.

### N.4. Item quality (раздел 116)
Задание оценивается по: fit, point-measure, DIF, дрейфу, SE(b). Сводный статус качества.

### N.5. Separation / reliability (разделы 117–119)
```
Separation G = SD_true / RMSE(SE)
Reliability = G² / (1 + G²)
```
- Item separation — насколько задания различимы по сложности.
- Person separation — на сколько статистически различимых уровней тест делит учеников.
- Reliability (аналог KR-20 / Cronbach в Раше). Порог для высоких ставок обычно ≥ 0.8–0.9.

**СДЕЛАНО.** `src/lib/rasch-separation.ts`, запись в `mock_tests` (миграция
102), вывод — `src/components/mock-reliability-panel.tsx` в отчёте по моку.

SD_true получается вычитанием дисперсий: `SD_true² = SD_наблюдаемое² − MSE`, где
`MSE = среднее SE²`. Отсюда крайний случай, ради которого заведён статус: если
наблюдаемый разброс не превышает погрешность, `SD_true²` отрицателен, корня нет,
и функция возвращает `NOT_SEPARABLE`, а не ноль (§217). Ноль читался бы как
«разделили, вышло плохо» вместо «разделить не удалось».

Число различимых уровней (то, о чём буквально спрашивает N.5) считается как
`strata = (4G+1)/3` — само G это отношение, а не количество уровней.

**Крайние меры исключены из основного числа, и это видно в данных.** У работы с
нулём верных (или со всеми верными) θ не существует, её значение получено
поправкой 0.3, и SE не измерена, а назначена. В RMSE она входит квадратом,
поэтому одна такая работа весит как тридцать обычных. Замер на реальных данных:

| вариант | person rel. | без крайних | item rel. | различимых уровней |
|---|---|---|---|---|
| Математика (36 чел., 55 заданий) | 0.495 | **0.736** | 0.716 | 2.6 |
| Ona Tili (54 чел., 49 заданий) | 0.692 | **0.796** | 0.893 | 3.0 |

Ни один вариант не дотягивает до 0.8 по ученикам. Разложение показывает, что
дело не в однородности когорты: на математике SD_true = 0.64 при RMSE = 0.38 —
разброс есть, измерение грубое. Лечится длиной теста и нацеливанием сложности
(см. «Почему баллы повторяются»), а не правкой формулы.

Чтобы исключение не выглядело подгонкой, рядом хранится
`person_reliability_with_extremes` и `person_extreme_count` — оба числа видны
в отчёте (§233).

### N.6. Trusted person / item (разделы 250, 251)
- Trusted person: валидные ответы, приемлемый person-fit, не FLAGGED/INVALID.
- Trusted item: калибрована на достаточной выборке, приемлемый fit, без сильного DIF/дрейфа, статус ACTIVE.

**Что хранить:** статусы качества, separation/reliability на вариант, person-fit, флаги.

## 16. Модуль O — Численная безопасность и детерминизм

### O.1. Numerical safety (раздел 200)
Защита от переполнения exp(), деления на ноль, log(0). Использовать устойчивые формы (log-sum-exp).

### O.2. Probability clipping (раздел 201)
P зажимать в [ε, 1−ε] (напр. ε = 1e−10) перед log — чтобы избежать бесконечностей. Фиксировать ε.

### O.3. Internal vs reporting rounding (разделы 202, 203)
Внутренние вычисления — полная точность (double). Округление только на выводе, по зафиксированному правилу. Никогда не округлять в середине итераций.

Одни и те же входные данные → бит-в-бит одинаковый результат. Любой стохастический шаг (EM, симуляция) — с фиксированным seed, который хранится.

**Что хранить:** ε клиппинга, seed, правила округления.

## 20. Главные алгоритмы (итоговые)

### 20.1. FIXED-FORM SCORING (раздел 241) — основной путь ученика
```
1. Собрать ответы ученика по фиксированному варианту.
2. Применить scoring (модуль A): X, статусы, частичный кредит, missing_policy=EXAM.
3. Загрузить калиброванные b_i / τ_ik нужной версии (проверить совместимость версий).
4. Оценить θ методом WLE (модуль C): итерации Ньютона до сходимости.
5. При non-convergence / экстремальном балле — обработать по политике (WLE даёт конечную θ).
6. Вычислить SE(θ) = 1/√I(θ).
7. Прогнать person-fit (модуль F/N) → quality_status.
8. Применить equating варианта на общую шкалу предмета (модуль K).
9. Трансформировать θ → S(0–75) (модуль L: A_scale, B_scale).
10. Применить пороги → уровень A+…C; посчитать ДИ балла.
11. Сформировать отчёт + provenance.
```

### 20.2. ITEM CALIBRATION (раздел 242)
```
1. Взять data_snapshot валидных ответов TRUSTED-персон.
2. Проверить связность банка (модуль E.11).
3. Оценить b_i / τ_ik выбранным estimator’ом (CML/MMLE), версионировать.
4. Проверить сходимость likelihood.
5. Диагностика: fit, point-measure, Q3, PCA, DIF (uz/ru), экстремальные задания.
6. Отбраковать/пометить проблемные задания (с логом).
7. Калибровка → DRAFT → проверка → APPROVED (иммутабельный снимок).
```

### 20.3. EQUATING (раздел 244)
```
1. Определить общие якоря / общих персон между формами.
2. Проверить connectivity; нет → LINKING_NOT_IDENTIFIABLE.
3. Проверить дрейф якорей, robust-очистка.
4. Оценить A, B (mean-mean или mean-sigma).
5. Применить к b и θ формы B.
6. Сохранить equating_uncertainty.
```

### 20.4. QUALITY ENGINE (раздел 249)
Единый прогон: person-fit, item-fit, separation/reliability, Q3, PCA, DIF, дрейф → сводный quality-отчёт по варианту и калибровке.

## 21. Правила целостности (NO SILENT ... — жёсткие запреты, разделы 233–240, 258–260, 263, 265)

Движок ОБЯЗАН соблюдать, нарушение = баг:
1. **NO SILENT FALLBACK** — не подменять метод «тихо» при сбое; возвращать статус.
2. **NO MAGIC COEFFICIENTS** — никаких чисел без математического происхождения.
3. **NO DIFFICULTY = POINTS** — сложность b ≠ баллы задания.
4. **NO BRANCH-SPECIFIC DIFFICULTY** — не держать разные b для uz/ru как норму (это как раз повод для DIF-проверки, а не «фича»).
5. **NO CROSS-SCALE MIXING** — не мешать θ/баллы разных шкал и предметов.
6. **NO SILENT 2PL/3PL** — не вводить дискриминацию/угадывание, продолжая называть это Рашем.
7. **NO SILENT HISTORICAL RECALCULATION** — не пересчитывать старые результаты «тихо».
8. **NO SILENT CATEGORY CHANGE** — collapsing категорий только явно, с версией.
9. Движок всегда знает `θ, b, P(θ,b), SE(θ), Fit`; никогда не теряет версии/снимки/пороги/якоря/исключения.
10. Каждая цифра имеет математическое происхождение. Движок — measurement engine, не score calculator.

# Часть II. Спецификация v4.0 (дословно)

Справочник разделов, на которые ссылается ТЗ v1.0 («раздел 241» и т.п.).
Перенос из `RASCH-SPEC-v4.0.docx` без изменений. Метка уровня после
названия раздела добавлена нами и частью нормы не является.
RASCH PSYCHOMETRIC ENGINE
MASTER TECHNICAL SPECIFICATION v4.0
Статус
Это полная спецификация психометрической логики Rasch Engine для образовательной assessment-платформы.
Документ определяет не UI, не dashboard, не роли пользователей и не дизайн продукта, а исключительно математическую и алгоритмическую механику психометрической системы.
Основное требование:
Реализация не должна просто знать НАИМЕНОВАНИЕ психометрического показателя. Она должна понимать, что этот показатель означает, из каких данных он получается, какой формулой вычисляется, каким алгоритмом оценивается, как интерпретируется и что делать в каждом особом случае.

### 0. ГЛАВНЫЙ ПРИНЦИП `CORE`

Система не должна работать как:
количество правильных ответов        ↓процент        ↓обычный балл        ↓оценка
Она должна работать как:
ответы  ↓scoring  ↓калиброванные параметры заданий  ↓Rasch probability model  ↓parameter estimation  ↓θ  ↓SE  ↓quality diagnostics  ↓scale transformation  ↓reported score / proficiency / decision

### 1. ОСНОВНЫЕ ОБЪЕКТЫ RASCH `CORE`

В базовой binary Rasch Model существуют два главных латентных параметра:
Person ability
θ_n
Способность человека n.
Item difficulty
b_i
Сложность задания i.
Оба параметра находятся на одной latent scale.

### 2. БИНАРНЫЙ ОТВЕТ `CORE`

Каждый ответ binary item представляет:
X_ni ∈ {0,1}
где:
1 = correct
0 = incorrect
Для missing response значение 0 не назначать автоматически.

### 3. ОСНОВНАЯ RASCH FORMULA `CORE`

Вероятность правильного ответа:
```
[ P_{ni} = e^{θ_n - b_i} / (1 + e^{θ_n - b_i}) ]
```
Эквивалентно:
```
[ P_{ni} = 1 / (1 + e^{-(θ_n - b_i)}) ]
```
Главное выражение:
```
[ θ_n - b_i ]
```
является разницей между ability человека и difficulty задания.

### 4. ИНТЕРПРЕТАЦИЯ РАЗНИЦЫ θ-b `CORE`

Если:
```
[ θ = b ]
```
то:
```
[ P = 0.5 ]
```
Если:
```
[ θ - b = 1 ]
```
то:
```
[ P ≈ 0.73 ]
```
Если:
```
[ θ - b = 2 ]
```
то:
```
[ P ≈ 0.88 ]
```
Если:
```
[ θ - b = -1 ]
```
то:
```
[ P ≈ 0.27 ]
```
Таким образом, ability и difficulty сравниваются непосредственно на одной шкале.

### 5. LOGIT `CORE`

Logit определяется:
```
[ logit(P) = ln[P / (1-P)] ]
```
Для Rasch:
```
[ logit(P_{ni}) = θ_n - b_i ]
```
Следовательно:
```
[ θ_n - b_i = ln[P_{ni} / (1-P_{ni})] ]
```
Logit — это не процент и не обычный балл.

### 6. ИДЕНТИФИКАЦИЯ ШКАЛЫ `CORE`

Rasch scale имеет произвольный ноль.
Если к каждому θ и b прибавить одну и ту же константу:
```
[ θ'_n = θ_n + c ]
```
```
[ b'_i = b_i + c ]
```
то:
```
[ θ'_n - b'_i = θ_n - b_i ]
```
следовательно, вероятности не меняются.
Поэтому calibration должна иметь identification constraint.
Production default:
```
[ Σ_{i=1}^{I} b_i = 0 ]
```
то есть:
```
[ mean(b) = 0 ]
```

### 7. RAW SCORE PERSON `CORE`

Для человека:
```
[ r_n = Σ_i X_{ni} ]
```
где r_n — количество correct responses.
В binary Rasch для фиксированного item set и известных item parameters raw score является sufficient statistic для person parameter.
Это означает:
при одинаковых:
- items
- calibration
- scoring
- estimator
одинаковый raw score приводит к одинаковому person estimate.

### 8. ПОЧЕМУ ОДИНАКОВЫЙ ПРОЦЕНТ НЕ ВСЕГДА ОДИНАКОВАЯ θ `CORE`

Например:
Form A:
20/40 = 50%
Form B:
20/40 = 50%
Это не гарантирует:
```
[ θ_A = θ_B ]
```
если difficulty distributions форм разные.
Поэтому сравнивать формы необходимо после common-scale linking/equating.

### 9. ITEM RAW SCORE `CORE`

Для item:
```
[ r_i = Σ_n X_{ni} ]
```
Это количество людей, ответивших правильно на item среди eligible observations.
Item difficulty оценивается не как
```
[ b_i = f(r_i) ]
```
а через соответствующую Rasch calibration procedure.

### 10. LIKELIHOOD PERSON `CORE`

Likelihood конкретного response pattern:
```
[ L(θ) = Π_i P_i^{X_i} (1-P_i)^{1-X_i} ]
```
Log-likelihood:
```
[ lnL(θ) = Σ_i [ X_i lnP_i + (1-X_i) ln(1-P_i) ] ]
```
MLE ищет:
```
[ θ̂_{MLE} = argmax_θ L(θ) ]
```

### 11. SCORE FUNCTION `CORE`

Производная log-likelihood для binary Rasch:
```
[ U(θ) = ∂lnL/∂θ = Σ_i (X_i - P_i) ]
```
MLE стремится решить:
```
[ U(θ) = 0 ]
```
То есть:
```
[ Σ_i X_i = Σ_i P_i ]
```
Интерпретация:
оценённая ability находится там, где ожидаемый raw score равен наблюдаемому raw score.

### 12. EXPECTED SCORE `CORE`

Для каждого item:
```
[ E(X_i|θ) = P_i(θ) ]
```
Для теста:
```
[ E(R|θ) = Σ_i P_i(θ) ]
```
где R — expected raw score.
Это Test Characteristic Function / Expected Score Function.

### 13. MONOTONICITY `CORE`

Поскольку:
```
[ ∂P/∂θ = P_i(1-P_i) > 0 ]
```
вероятность правильного ответа растёт при увеличении θ.
Следовательно:
```
[ ∂E(R|θ)/∂θ > 0 ]
```
для непустого набора items.
Это важное свойство должно сохраняться.

### 14. NEWTON-RAPHSON / FISHER SCORING `CORE`

Fisher information:
```
[ I(θ) = -E[∂²lnL/∂θ²] ]
```
Для binary Rasch:
```
[ I(θ) = Σ_i P_i(1-P_i) ]
```
Newton/Fisher update:
```
[ θ_{new} = θ_{old} + U(θ_{old}) / I(θ_{old}) ]
```
то есть:
```
[ θ_{new} = θ_{old} + (Σ_i X_i - Σ_i P_i) / I(θ_{old}) ]
```

### 15. ИТЕРАЦИОННАЯ ESTIMATION PROCEDURE `CORE`

Person estimation:
1. Получить valid responses.
2. Получить calibrated b_i.
3. Выбрать начальную θ.
4. Для каждого item вычислить P_i.
5. Вычислить U(θ).
6. Вычислить I(θ).
7. Выполнить update.
8. Проверить convergence.
9. Если convergence отсутствует — повторить.
10. Достигнут max iterations → NON_CONVERGED.
11. После convergence получить θ.
12. Вычислить SE.
13. Выполнить quality diagnostics.

### 16. НАЧАЛЬНАЯ θ `CORE`

Допустимые стратегии:
- mean item difficulty
- population mean
- prior mean
- previous valid linked measure
routing estimate для CAT.
Стратегия должна быть частью estimator configuration.

### 17. CONVERGENCE `CORE`

Convergence означает, что дальнейшие итерации почти не изменяют estimate.
Использовать минимум:
```
[ |θ_{t+1} - θ_t| < ε ]
```
Дополнительно:
```
[ |b_{t+1} - b_t| < ε ]
```
Оба значения должны быть configuration parameters.
Например:
```
[ ε = 0.001 ]
```
может быть production default, но не является универсальным психометрическим законом.

### 18. MAX ITERATIONS `CORE`

Установить:
MAX_ITERATIONS
При превышении:
status = NON_CONVERGED
Нельзя выдавать обычный official estimate без явно предусмотренного fallback.

### 19. EXTREME SCORE `CORE`

Если:
```
[ r = 0 ]
```
обычный MLE стремится к:
```
[ θ → -∞ ]
```
Если:
```
[ r = L ]
```
то:
```
[ θ → +∞ ]
```
где L — количество eligible items.
Это нормальное свойство MLE.

### 20. FINITE ESTIMATION `CORE`

Для extreme scores production engine должен применять явно выбранный метод:
- WLE
- MAP
- EAP
либо другой заранее утверждённый estimator.
Нельзя просто заменить ∞ на 10.

### 21. MLE `CORE`

Maximum Likelihood:
```
[ θ̂_{MLE} = argmax_θ L(θ) ]
```
Преимущество:
не требует prior.
Недостаток:
extreme score может привести к бесконечному estimate.

### 22. WLE `CORE`

Weighted Likelihood Estimation корректирует bias conventional MLE, особенно в finite samples.
WLE должен быть реализован как отдельный estimator version.
Нельзя считать WLE и MLE одинаковым numerical result.

### 23. MAP `CORE`

MAP:
```
[ θ̂_{MAP} = argmax_θ [L(θ) · g(θ)] ]
```
или:
```
[ θ̂_{MAP} = argmax_θ [lnL(θ) + ln g(θ)] ]
```
где π(θ) — prior.

### 24. EAP `CORE`

EAP:
```
[ θ̂_{EAP} = ∫ θ L(θ) g(θ) dθ  /  ∫ L(θ) g(θ) dθ ]
```
EAP является posterior mean.

### 25. BAYESIAN PRIOR `CORE`

Если используется MAP/EAP, хранить:
- distribution type
- mean
- variance
- SD
prior version.
Изменение prior должно создавать новую estimator configuration/version.

### 26. ITEM INFORMATION `CORE`

Для binary Rasch:
```
[ I_i(θ) = P_i(1-P_i) ]
```
Поскольку:
```
[ P_i = P_i(θ) ]
```
получаем:
```
[ I_i(θ) = P_i(θ) [1 - P_i(θ)] ]
```

### 27. MAXIMUM ITEM INFORMATION `CORE`

При:
```
[ P = 0.5 ]
```
получаем:
```
[ I_i = 0.25 ]
```
Это происходит когда:
```
[ θ = b_i ]
```
Поэтому item наиболее информативен около своей difficulty.

### 28. TEST INFORMATION `CORE`

При local independence:
```
[ I_{test}(θ) = Σ_i I_i(θ) ]
```
то есть:
для каждого θ:    для каждого item:        вычислить P_i        вычислить I_i    сложить I_i

### 29. STANDARD ERROR `CORE`

При обычном large-sample approximation:
```
[ SE(θ) = 1 / √I(θ) ]
```
Чем больше information, тем меньше uncertainty.

### 30. INFORMATION И SE — НЕ ОДНО И ТО ЖЕ `CORE`

Information описывает потенциальную precision теста в конкретном месте шкалы.
SE описывает uncertainty конкретного estimated measure.
Reliability и separation являются другими sample-level indicators.
Их нельзя смешивать.

### 31. OBSERVED INFORMATION `CORE`

Помимо expected Fisher information допускается использовать observed information:
```
[ J(θ) = -∂²lnL/∂θ² ]
```
Для standard binary Rasch структура тесно связана с:
```
[ Σ_i P_i(1-P_i) ]
```
Но engine должен явно знать, какой тип information используется каждым estimator.

### 32. CONFIDENCE INTERVAL `CORE`

При приблизительном normal approximation:
```
[ CI_{95%} = θ ± 1.96 · SE(θ) ]
```
Для extreme/Bayesian/нестандартных случаев engine должен использовать соответствующую interval methodology, если она включена.

### 33. DIFFERENCE BETWEEN TWO MEASURES `CORE`

Для независимых measures:
```
[ SE(Δ) = √[SE_1² + SE_2²] ]
```
где:
```
[ Δ = θ_1 - θ_2 ]
```
Если measurements correlated:
```
[ Var(Δ) = Var(θ_1) + Var(θ_2) - 2Cov(θ_1,θ_2) ]
```
Следовательно:
```
[ SE_Δ = √Var(Δ) ]
```

### 34. ITEM TARGETING `CORE`

Item targeting сравнивает:
```
[ distribution(b_i) ]
```
с:
```
[ distribution(θ_n) ]
```
Если большая часть persons выше всех items:
ceiling problem.
Если ниже всех items:
floor problem.

### 35. PERSON-ITEM MAP `CORE`

Для каждого construct анализировать две distributions:
Persons:  θItems:    b
Они должны иметь достаточное overlap.

### 36. TEST CHARACTERISTIC CURVE `CORE`

Для каждой θ вычислять:
```
[ E(R|θ) = Σ_i P_i(θ) ]
```
Эта функция показывает ожидаемый raw score при данной ability.
Используется для:
- targeting
- test design
- score transformation
анализа формы.

### 37. ICC `CORE`

Item Characteristic Curve:
```
[ P_i(θ) = logistic(θ - b_i) ]
```
График должен быть монотонным и иметь midpoint в:
```
[ θ = b_i ]
```
для classic binary Rasch.

### 38. FIT — ОБЩЕЕ ОПРЕДЕЛЕНИЕ `CORE`

Fit показывает, насколько observed responses соответствуют тому, что модель ожидает.
Сначала для observation:
```
[ e_{ni} = X_{ni} - P_{ni} ]
```
Это residual.

### 39. EXPECTED VARIANCE `CORE`

Для binary response:
```
[ V_{ni} = P_{ni}(1-P_{ni}) ]
```
Это модельная variance конкретного observation.

### 40. STANDARDIZED RESIDUAL `CORE`

```
[ z_{ni} = e_{ni} / √V_{ni} ]
```
Следовательно:
```
[ z_{ni}² = (X_{ni}-P_{ni})² / [P_{ni}(1-P_{ni})] ]
```

### 41. OUTFIT MNSQ `CORE`

Outfit — outlier-sensitive fit.
Для item:
```
[ Outfit_i = (1/N) Σ_n z_{ni}² ]
```
то есть:
```
[ Outfit_i = (1/N) Σ_n (X_{ni}-P_{ni})² / [P_{ni}(1-P_{ni})] ]
```
Outfit сильнее чувствителен к неожиданным ответам на items, далеко расположенным от estimated ability.

### 42. INFIT MNSQ `CORE`

Infit — information-weighted fit.
Для item:
```
[ Infit_i = Σ_n (X_{ni}-P_{ni})² / Σ_n V_{ni} ]
```
Это эквивалентно:
```
[ Infit_i = Σ_n W_{ni} z_{ni}² / Σ_n W_{ni},  где W_{ni}=V_{ni} ]
```
Infit сильнее чувствителен к unexpected responses, которые находятся в более информативной части измерительной шкалы.

### 43. ОТКУДА БЕРУТСЯ INFIT И OUTFIT `CORE`

Алгоритм:
Для каждого eligible response:
1. Получить X.
2. Получить θ person.
3. Получить b item.
4. Рассчитать P.
5. Рассчитать V=P(1-P).
6. Рассчитать residual=X-P.
7. Рассчитать z=residual/sqrt(V).
8. z² участвует в Outfit.
9. residual² и V участвуют в Infit.
10. После обработки всех observations рассчитать MNSQ.

### 44. ИНТЕРПРЕТАЦИЯ MNSQ `CORE`

Теоретический reference value:
```
[ E(MNSQ) = 1 ]
```
Если:
```
[ MNSQ > 1 ]
```
наблюдается больше непредсказуемости, чем ожидает модель.
Если:
```
[ MNSQ < 1 ]
```
данные более predictable, чем ожидалось.
Например:
1.20 означает примерно 20% больше residual variation относительно reference level 1.
Но конкретный decision threshold должен быть policy-dependent, а не считаться универсальным законом.

### 45. OVERFIT `CORE`

Слишком низкий MNSQ может означать:
- чрезмерную predictability
- искусственную redundancy
- deterministic response pattern
- local dependence
scoring artefact.
Overfit также нужно исследовать, а не просто считать «хорошим».

### 46. UNDERFIT `CORE`

Высокий MNSQ может возникнуть из-за:
- noise
- multidimensionality
- wrong key
- DIF
- local dependence
- guessing
- careless mistakes
content mismatch.

### 47. ZSTD `CORE`

Mean-square может быть transformed в standardized statistic.
Например для Outfit возможно использование Wilson-Hilferty transformation.
ZSTD показывает отклонение от expected fit с учётом sampling distribution.
Он зависит от sample size и поэтому не должен рассматриваться отдельно от MNSQ.

### 48. ITEM FIT VS PERSON FIT `CORE`

Для item:
суммирование идёт по persons.
Для person:
суммирование идёт по items.
Person Outfit:
```
[ Outfit_n = (1/L) Σ_i z_{ni}² ]
```
Person Infit:
```
[ Infit_n = Σ_i (X_{ni}-P_{ni})² / Σ_i V_{ni} ]
```

### 49. POINT-MEASURE CORRELATION `CORE`

Для diagnostic analysis можно рассчитывать correlation между item score and person measure.
Идея:
если higher ability persons чаще отвечают correctly, correlation обычно положительная.
Сильно отрицательное значение может указывать на:
- wrong key
- miskeyed item
- reversed scoring
severe anomaly.
Однако point-measure correlation не заменяет Rasch fit.

### 50. LOCAL INDEPENDENCE `CORE`

Local independence означает:
после conditioning on latent trait ответы на разные items не должны оставаться зависимыми.
Формально:
```
[ P(X_1,…,X_L|θ) = Π_i P(X_i|θ) ]
```
если observations locally independent.

### 51. YEN Q3 `CORE`

После получения standardized residuals анализировать item pair:
```
[ Q3_{ij} = corr(z_i, z_j) ]
```
Q3 используется для обнаружения residual dependency между items.
Особенно важно для:
- shared passage
- shared stimulus
- repeated content
sequential dependency.

### 52. ПОЧЕМУ Q3 НУЖЕН `CORE`

Пример:
Question 2 содержит информацию, которая помогает решить Question 3.
Тогда responses могут быть correlated даже после учёта ability.
Это нарушает assumption:
```
[ P(X_i,X_j|θ) = P(X_i|θ) · P(X_j|θ) ]
```

### 53. Q3 АНАЛИЗ `CORE`

Для каждой pair:
1. Получить persons with valid responses на оба items.
2. Получить model residuals.
3. Рассчитать residual correlation.
4. Сравнить с reference distribution.
5. Проверить magnitude.
6. Проверить content relation.
7. Проверить testlet/passage relation.
8. Создать dependency flag.
Не использовать одно универсальное значение Q3 как абсолютный автоматический delete threshold.

### 54. TESTLET `CORE`

Если группа items зависит от одного stimulus:
создать conceptual testlet.
Например:
Passage A ├─ Question 1 ├─ Question 2 ├─ Question 3 └─ Question 4
Проверить residual dependency внутри группы.

### 55. СПОСОБЫ ОБРАБОТКИ TESTLET `CORE`

Варианты:
- переписать items
- уменьшить dependency
- объединить в super-item
- использовать testlet model/extension
оставить, если dependency несущественная и precision policy это допускает.
Но нельзя игнорировать dependency, если она существенно искажает precision.

### 56. DIMENSIONALITY `CORE`

Rasch scale предполагает dominant latent dimension.
Проверять:
- residual PCA
- residual contrasts
- residual correlations
- item content
- DIF
subgroup patterns.

### 57. RESIDUAL PCA `CORE`

После удаления основного Rasch dimension анализируются residuals.
Цель:
определить, остаётся ли структурированная информация, которую основной θ не объясняет.
Если появляется устойчивый second dimension:
исследовать scale structure.

### 58. MARTIN-LÖF TEST `CORE`

Martin-Löf type test используется как дополнительная проверка Rasch invariance/unidimensionality путём разделения item set и проверки согласованности модели между подмножествами.
Не использовать его как единственный критерий dimensionality.

### 59. ANDERSEN LR TEST `OPTIONAL`

Разделить population на две или более группы по заранее определённому правилу.
Например:
low-score groupvshigh-score group
Оценить item parameters условно для групп и проверить, согласуются ли они с invariant Rasch structure.
Концептуально:
```
[ LR = -2 [lnL_{restricted} - lnL_{alternative}] ]
```
где:
- restricted model = invariant item parameters
alternative = разные item parameters между группами.
При большом sample statistic сопоставляется с соответствующим reference distribution.
Andersen LR является глобальной проверкой Rasch-specific invariance, поэтому его нельзя заменять простым сравнением raw percentages.

### 60. DIF `CORE`

DIF означает:
при одинаковой latent ability item работает по-разному для групп.
Пусть:
```
[ b_{i,A} ]
```
и:
```
[ b_{i,B} ]
```
получены после соответствующего linking/identification.
Тогда:
```
[ DIF_i = b_{i,A} - b_{i,B} ]
```
Направление определяется заранее утверждённой convention.

### 61. DIF STANDARD ERROR `CORE`

Если estimates независимы:
```
[ SE(DIF_i) = √[SE(b_{i,A})² + SE(b_{i,B})²] ]
```
Если estimates correlated:
```
[ Var(DIF) = Var(b_A) + Var(b_B) - 2Cov(b_A,b_B) ]
```

### 62. DIF Z `CORE`

```
[ Z_{DIF} = DIF_i / SE(DIF_i) ]
```
Но statistical significance не равна practical significance.

### 63. DIF EFFECT SIZE `CORE`

Engine должен одновременно хранить:
- absolute DIF magnitude
- direction
- SE
- significance
- practical effect category
group sample sizes.
Решение:
statistical evidence+effect magnitude+content interpretation+sample adequacy

### 64. MULTIPLE TESTING DIF `CORE`

Если тестируется множество items:
не интерпретировать сотни p-values без correction/overall policy.
Поддерживать:
- raw p
- adjusted p
- FDR или другой approved procedure
effect-size threshold.

### 65. DIF ПО BRANCH `CORE`

Branch можно использовать как grouping factor:
Branch A vs Branch B.
Но branch difference не является автоматически DIF.
Исследовать:
- curriculum
- sample
- language
- instruction
- exposure
item functioning.

### 66. ITEM DRIFT `CORE`

Drift:
```
[ Δb_i = b_{i,t2} - b_{i,t1} ]
```
Если:
```
[ |Δb_i| > threshold ]
```
становится существенным относительно uncertainty/stability criteria, item помечается для investigation.
Причины могут быть:
- curriculum change
- wording change
- population change
- exposure
- leak
- real construct change
calibration differences.

### 67. DRIFT STANDARDIZED DIFFERENCE `CORE`

Для приблизительно независимых estimates:
```
[ z_{drift} = Δb_i / SE(Δb_i) ]
```
При зависимости учитывать covariance.

### 68. ITEM EXPOSURE `CORE`

Хранить:
```
[ ExposureRate_i = (число предъявлений item_i) / (число участников) ]
```
В зависимости от CAT design denominator может быть определён иначе.
Exposure используется для security monitoring и exposure-control algorithms.

### 69. REPEATED ITEM EFFECT `CORE`

Повторное использование может привести к:
- memory
- practice
- familiarity
leakage.
Поэтому response data после known exposure может иметь отдельный calibration status.

### 70. INVALID ITEM `CORE`

Если выявлен wrong key:
не менять старый key silently.
Создать новый item version.

### 71. ITEM VERSION `CORE`

Изменение:
- text
- options
- key
- image
- stimulus
- scoring
создаёт новую item version.

### 72. SCORING BEFORE RASCH `CORE`

Перед Rasch estimation response должен пройти scoring.
Pipeline:
raw response ↓item version ↓scoring rule ↓0/1 или category score ↓validity state ↓Rasch engine

### 73. MISSING `CORE`

Missing не равен wrong.
Default conceptual states:
CORRECTINCORRECTOMITTEDNOT_REACHEDTECHNICAL_FAILUREINVALIDATED
Каждый state обрабатывается scoring policy.

### 74. NOT REACHED `CORE`

Если student не дошёл до item из-за time limit:
не превращать автоматически в incorrect, если assessment specification определяет его как not reached.

### 75. MULTI-ATTEMPT `CORE`

Каждая attempt является отдельным response evidence.
Не делать:
```
[ θ_{cumulative} ≠ mean(θ_{attempt1}, θ_{attempt2}, …) ]
```
простым arithmetic mean без специальной longitudinal methodology.

### 76. LONGITUDINAL CHANGE `OPTIONAL`

Если forms находятся на одной linked scale:
```
[ Δθ = θ_{t2} - θ_{t1} ]
```
При интерпретации учитывать:
```
[ SE_{Δθ} = √[SE(θ_{t1})² + SE(θ_{t2})²] ]
```
и scale linking uncertainty.

### 77. RESPONSE TIME `OPTIONAL`

Response time:
не часть classic Rasch ability.
Хранить отдельно:
```
[ RT = t_{submit} - t_{start} ]
```
Если speed становится частью psychometric model, это отдельная model extension.

### 78. RASCH POLYTOMOUS MODELS `CORE`

Если response принимает:
```
[ X ∈ {0, 1, 2, …, m} ]
```
использовать соответствующую polytomous Rasch model.

### 79. PARTIAL CREDIT MODEL `CORE`

Для PCM вероятность категории определяется через category-step parameters.
Одна из стандартных parameterizations:
```
[ P(X_{ni}=k|θ) = exp[Σ_{j=0}^{k}(θ_n - δ_{ij})] / Σ_{h=0}^{m} exp[Σ_{j=0}^{h}(θ_n - δ_{ij})] ]
```
с нормировочной convention для первого step.
Здесь:
- θ_n — ability
- δ_is — item-specific step parameters
k — category.
PCM позволяет разным items иметь разные category structures.

### 80. RATING SCALE MODEL `CORE`

RSM использует общую category structure для группы items.
Conceptually:
```
[ log[P_{ik} / P_{i,k-1}] = θ_n - b_i - τ_k ]
```
где:
- b_i — item location
τ_k — common category threshold/step.
RSM применяется, когда items используют одну и ту же rating-scale structure.

### 81. PCM VS RSM `CORE`

Использовать:
RSM
если category structure общая.
PCM
если category structure может отличаться item-to-item.
Нельзя выбирать между ними только потому, что одна модель даёт «лучше выглядящий score».
Учитывать:
- content
- category structure
- fit
- stability
interpretability.

### 82. POLYTOMOUS EXPECTED SCORE `CORE`

Для item:
```
[ E(X_i|θ) = Σ_{k=0}^{m_i} k · P_{ik}(θ) ]
```
Для всего теста:
```
[ E(R|θ) = Σ_i E(X_i|θ) ]
```

### 83. POLYTOMOUS VARIANCE `CORE`

Для item:
```
[ Var(X_i|θ) = E(X_i²|θ) - [E(X_i|θ)]² ]
```
где:
```
[ E(X_i²|θ) = Σ_k k² · P_{ik}(θ) ]
```
Эта variance используется при информации и fit calculations.

### 84. CATEGORY FUNCTIONING `CORE`

Проверять:
- frequency
- probability curves
- thresholds
- ordering
- category fit
category information.

### 85. DISORDERED THRESHOLDS `CORE`

Если:
```
[ τ_1 > τ_2 ]
```
или другой порядок противоречит intended category progression, возникает threshold disordering.
Не исправлять автоматически.
Исследовать:
- category wording
- scoring
- sparse use
- respondent interpretation
overlapping categories.

### 86. CATEGORY COLLAPSING `CORE`

Если категории объединяются:
создать новую scoring/model version.
Не перезаписывать старую calibration.

### 87. MANY-FACET RASCH MODEL `OPTIONAL`

MFRM расширяет Rasch при наличии дополнительных facets:
- person
- item
- rater
- task
- criterion
другие оценочные facets.
Для rating categories стандартная форма может быть представлена:
```
[ ln[P_{nijk} / P_{nij,k-1}] = B_n - D_i - C_j - F_k ]
```
в зависимости от выбранной facet parameterization.
Где:
- B_n — person ability
- D_i — item difficulty
- C_j — rater severity
- H_k — task/facet parameter
F_k — category step.
Официальные Rasch facet formulations задают именно относительное положение ability, item difficulty, rater severity и category steps на common logit scale.

### 88. RATER SEVERITY `OPTIONAL`

Rater severity показывает относительную строгость проверяющего.
Если:
```
[ C_j > 0 ]
```
при принятой convention rater более строг относительно reference point.
Если:
```
[ C_j < 0 ]
```
rater менее строг.
Ноль определяется identification constraint.

### 89. ПОЧЕМУ НЕЛЬЗЯ СЧИТАТЬ SEVERITY КАК «СРЕДНИЙ ПРОЦЕНТ» `OPTIONAL`

Нельзя:
```
[ severity ≠ 1 - mean(score) ]
```
потому что rating depends simultaneously on:
- person ability
- item difficulty
- category structure
- task
rater.
Severity оценивается как facet parameter внутри многогранной likelihood model.

### 90. MFRM ESTIMATION `OPTIONAL`

Для каждого observation:
1. Получить person.
2. Получить item.
3. Получить rater.
4. Получить task/criterion.
5. Получить category.
6. Построить model probability.
7. Рассчитать residual.
8. Рассчитать likelihood.
9. Обновить facet parameters.
10. Повторить до convergence.
11. Рассчитать SE для каждого facet.
12. Рассчитать fit каждого facet.

### 91. RATER FIT `OPTIONAL`

Для каждого rater:
использовать те же residual-based procedures:
```
[ Infit_j = Σ (X-E)² · W / Σ W ]
```
```
[ Outfit_j = (1/N_{observations}) Σ z² ]
```
Проверять:
- severity
- SE
- Infit
- Outfit
- consistency
unexpected patterns.

### 92. RATER SEVERITY COMPARISON `OPTIONAL`

Для двух calibrations:
```
[ Z = (C_{j1} - C_{j2}) / √[SE(C_{j1})² + SE(C_{j2})²] ]
```
если estimates independent.
Такая логика используется для сравнения facet severities между administrations.

### 93. RATER DESIGN `OPTIONAL`

Для идентификации severity необходима connected design.
Если:
- rater A оценивает только лёгкие items
- rater B только сложные
невозможно чисто отделить rater severity от item difficulty.
Нужна достаточная cross-rating connectivity.

### 94. LLTM `FUTURE`

Linear Logistic Test Model представляет item difficulty через item components.
Концептуально:
```
[ b_i = Σ_k q_{ik} η_k ]
```
где:
- q_ik — присутствие/weight component k в item i
η_k — estimated contribution component.

### 95. LLTM ЧТО ОЗНАЧАЕТ `FUTURE`

Например item имеет:
algebra = 1word_problem = 1multi_step = 1graph = 0
Тогда:
```
[ b_i = η_{algebra} + η_{word} + η_{multi-step} ]
```
LLTM оценивает вклад структурных components.
Это не означает, что заранее можно идеально знать future difficulty.

### 96. LLTM PREDICTED VS EMPIRICAL `FUTURE`

Новая item:
```
[ b_{predicted} = Σ_k q_{ik} η_k ]
```
После field data:
```
[ b_{empirical} ]
```
Система должна сравнить:
```
[ Δ_i = b_{empirical} - b_{predicted} ]
```
Большое отличие → diagnostic investigation.

### 97. MULTIDIMENSIONAL RASCH `FUTURE`

Если item зависит от нескольких dimensions:
```
[ θ = (θ_1, θ_2, …, θ_K) ]
```
Не использовать обычную одномерную:
```
[ не сводится к одномерной разнице θ - b ]
```
если модель действительно multidimensional.
Конкретная MDRM parameterization должна быть указана в model version.

### 98. MDRM ITEM STRUCTURE `FUTURE`

Для item хранить association with dimensions.
Например:
item ├─ Math reasoning └─ Reading comprehension
Но это должно быть теоретически обосновано.

### 99. MDRM RESULT `FUTURE`

Не возвращать:
one arbitrary theta
из нескольких dimensions.
Возвращать:
```
[ (θ_1, θ_2, …, θ_K) ]
```
либо заранее определённую theoretically justified composite measure.

### 100. MIXED RASCH `FUTURE`

Mixed Rasch Model предполагает наличие latent classes.
Концептуально:
```
[ P(X|θ) = Σ_c π_c · P(X|θ,c) ]
```
где:
- c — latent class
π_c — class probability.
Каждая class может иметь собственную parameter structure согласно выбранной model specification.

### 101. MIXTURE ESTIMATION `FUTURE`

Обычно используется iterative latent-class estimation, например EM:
1. Инициализировать classes.
2. E-step: вычислить posterior probability принадлежности person к class.
3. M-step: обновить class parameters.
4. Проверить likelihood/convergence.
5. Повторить.

### 102. CLASS LABEL SWITCHING `FUTURE`

Latent class 1 и class 2 могут менять numerical labels между runs.
Поэтому применять canonical ordering:
например по class mean ability.
Не менять исторические labels без versioned transformation.

### 103. CML `CORE`

Conditional Maximum Likelihood использует conditioning на person raw scores для устранения person parameters из conditional likelihood item calibration.
Conceptual pipeline:
raw scores persons ↓conditional likelihood ↓item parameters ↓scale identification
CML особенно соответствует Rasch-specific item calibration framework.

### 104. JMLE `CORE`

Joint Maximum Likelihood:
```
[ (θ̂, b̂) = argmax_{θ,b} L(θ,b|X) ]
```
Одновременно оцениваются persons и items.
Необходимо учитывать finite-sample bias characteristics.

### 105. MMLE `CORE`

Marginal Maximum Likelihood рассматривает person ability как latent random variable.
```
[ P(X|b) = ∫ P(X|θ,b) · g(θ) dθ ]
```
где:
g(θ) — latent ability distribution.
Item parameters оцениваются по marginal likelihood.

### 106. EM ДЛЯ MMLE `CORE`

E-step
При текущих item parameters вычислить posterior latent distribution.
M-step
Обновить item parameters и, если предусмотрено, параметры latent distribution.
Повторять:
```
[ E-step → M-step → повторять до convergence ]
```
до convergence.

### 107. LIKELIHOOD CONVERGENCE `CORE`

Каждый estimator хранит:
- initial values
- iterations
- final log-likelihood
- max parameter delta
- likelihood delta
convergence status.

### 108. PAIRWISE ESTIMATION `OPTIONAL`

Поддержать Pairwise Estimation как альтернативный calibration method для неполных/sparse matrices.
Результат должен быть:
- estimates
- SE
- convergence/status
- scale identification
dataset snapshot.
Не использовать Pairwise как скрытую замену CML.

### 109. ESTIMATOR VERSIONING `CORE`

Результат всегда должен знать:
model = RASCH_BINARYestimator = WLEestimator_version = ...configuration = ...

### 110. CALIBRATION DATA SNAPSHOT `CORE`

Перед calibration:
responses ↓eligibility filtering ↓immutable snapshot ↓calibration
Snapshot нельзя менять после запуска.

### 111. CALIBRATION ELIGIBILITY `CORE`

Каждое observation классифицировать.
Минимально:
VALIDOMITTEDNOT_REACHEDTECHNICAL_FAILUREINVALIDDUPLICATECONTAMINATEDEXCLUDED

### 112. CONTAMINATION `CORE`

Если response подозрителен:
не уничтожать raw data.
Хранить:
raw = retained
calibration_eligible = false
reason = ...

### 113. CHEATING И RASCH `CORE`

Cheating не является Rasch parameter.
Rasch engine может показать anomalous fit, но не должен заявлять:
«этот человек точно списывал»
только на основании fit statistic.

### 114. PERSON MISFIT `CORE`

Person misfit может быть обусловлен:
- random responding
- inconsistent response pattern
- multidimensionality
- guessing
- content-specific knowledge
careless errors.
Person measure можно математически получить, но quality status должен отражать misfit.

### 115. QUALITY STATUS `CORE`

Каждый result должен иметь:
VALID_HIGH_PRECISIONVALID_ACCEPTABLELOW_PRECISIONEXTREME_ESTIMATEPERSON_MISFITNON_CONVERGEDINSUFFICIENT_INFORMATIONINVALIDREVIEW_REQUIRED

### 117. ITEM SEPARATION `CORE`

Item separation показывает, насколько spread item measures велик относительно их uncertainty.
Для sample-level analysis может использоваться форма:
```
[ G_{items} = SD(b) / RMSE_{items} ]
```
Точная reported form зависит от выбранной Rasch software convention.

### 118. PERSON SEPARATION `CORE`

Аналогично:
```
[ G_{persons} = SD(θ) / RMSE_{persons} ]
```
Но individual SE остаётся главным показателем precision конкретного результата.

### 119. RELIABILITY `CORE`

Separation reliability в одной распространённой форме:
```
[ Reliability = G² / (1 + G²) ]
```

Но обязательно фиксировать exact definition, потому что разные implementation conventions существуют.

### 120. ANCHORS `CORE`

### 121. COMMON-ITEM LINKING `CORE`


### 122. LINEAR SCALE TRANSFORMATION `CORE`

Общая transformation:
```
[ x' = A·x + B ]
```
Она изменяет numerical representation, но сохраняет порядок и относительное расположение при A>0.

### 123. MEAN-MEAN LINKING `CORE`

### 124. MEAN-SIGMA LINKING `CORE`

Получается transformation, согласующая location и spread anchor set.

### 125. ANCHOR DRIFT `CORE`

### 126. ROBUST ANCHOR CLEANING `CORE`

Для anchor shifts использовать robust diagnostics:
```
[ z_i = (Δb_i - median(Δb)) / MAD ]
```
при используемой robust normalizing convention.
Но outlier не равен автоматически bad anchor.
После statistical flag требуется investigation.

### 131. STANDARD SETTING `CORE`

### 132. BOOKMARK METHOD `CORE`

Порядок:
1. Откалибровать items.
2. Упорядочить items по difficulty/location.

7. Собрать judgments.

### 145. WHY NOT ALWAYS SELECT MAX INFORMATION `FUTURE`

### 146. SYMPSON-HETTER `FUTURE`

После selection item может пройти exposure gate.
Концептуально:
```
[ P(Administer_i) = P(Selected_i) · P(Administer_i | Selected_i) ]
```

### 147. SYMPSON-HETTER ALGORITHM `FUTURE`

1. Рассчитать information ranking.
2. Выбрать candidate item.
3. Получить control probability p_i.
4. Random gate.
5. Если gate passed → administer.
6. Если gate failed → следующий eligible item.
7. Update exposure statistics.
Exposure probability является частью algorithm configuration.

### 149. SHADOW TEST `FUTURE`

### 174. RASCH MODEL НЕ ДЕЛАЕТ CHEATING DETECTION `CORE`

### 175. STANDARD ERROR OF ITEM `CORE`

В calibration каждый b_i должен иметь estimated uncertainty.
В зависимости от calibration estimator она получается из соответствующей information/Hessian/conditional likelihood estimation procedure.

### 176. HESSIAN `CORE`

При likelihood-based estimation Hessian:
```
[ H(η) = ∂²lnL / ∂η∂η' ]
```
где η — vector of estimated parameters.
Approximate covariance:
```
[ Cov(η) ≈ (-H)^{-1} ]
```
при соответствующих regularity conditions.

### 177. COVARIANCE MATRIX `CORE`

При многопараметрической calibration полезно хранить:
```
[ Cov(η) ]
```
или достаточную information representation.
Это необходимо для корректного расчёта uncertainty при:
- differences
- contrasts
- linking
facets.

### 178. CONTRAST `CORE`

Для сравнения двух parameters:
```
[ C = a'η ]
```
Variance:
```
[ Var(C) = a'Cov(η)a ]
```
SE:
```
[ SE(C) = √Var(C) ]
```
Это более корректно, чем всегда предполагать независимость.

### 179. MFRM CONTRAST `OPTIONAL`

Например:
```
[ C = C_{raterA} - C_{raterB} ]
```
можно оценивать через covariance matrix.

### 180. CATEGORY STEP ESTIMATION `CORE`

Для PCM/RSM category thresholds оцениваются вместе с другими parameters через соответствующую likelihood.
Нельзя получать thresholds simple arithmetic averages of category percentages.

### 181. EXPECTED CATEGORY `CORE`

Для polytomous item:
```
[ P_{ik}(θ) ]
```
вычисляется для каждой category.
Затем:
```
[ E(X_i|θ) = Σ_k k · P_{ik}(θ) ]
```

### 182. POLYTOMOUS INFORMATION `CORE`

General information для ordered categorical item может вычисляться через derivative expected score:
```
[ I_i(θ) = Var[X_i|θ] ]
```
при canonical Rasch formulation.
То есть:
```
[ I_i(θ) = Σ_k (k - E_i)² · P_{ik}(θ) ]
```

### 183. POLYTOMOUS FIT `CORE`

Для category observation:
```
[ Residual = X - E(X|θ) ]
```
```
[ Variance = Var(X|θ) ]
```
```
[ z = Residual / √Variance ]
```
Далее аналогично формируются:
- Outfit
Infit.
Rasch documentation использует именно residual и modelled variance для category fit calculations.

### 184. MISSING POLYTOMOUS `CORE`

Не считать:
missing = category 0.
Missing должен быть исключён из likelihood согласно missing/scoring policy.

### 185. RATING SCALE VALIDITY `CORE`

### 215. RESULT QUALITY VS RESULT EXISTENCE `CORE`

# Часть III. Дополнения к спецификации

Разделы 267+. Взяты не для полноты: каждый закрывает пробел, который мешает
именно нашей цели. Нумерация продолжает норму.

### 267. WLE — ФОРМУЛА ПОПРАВКИ WARM `CORE`

§22 называет WLE и требует держать его отдельной версией estimator-а, но
формулы не даёт — реализовать по такому описанию нельзя.

У MLE на конечном тесте есть смещение к краям шкалы, из-за него крайние оценки
уходят в бесконечность (§19). Warm (1989) добавляет к score function поправку:

```
[ U_W(θ) = Σ_i (x_i − P_i) + J(θ) / (2·I(θ)) ]
```

где:

```
[ I(θ) = Σ_i P_i(1−P_i) ]
[ J(θ) = Σ_i P_i(1−P_i)(1−2P_i) ]
```

Итерации Newton-Raphson те же, что в §14, только `U(θ)` заменяется на `U_W(θ)`.

```
[ SE(θ̂) ≈ 1 / √I(θ̂) ]
```

Главное свойство: WLE даёт **конечную** оценку и при 0 верных, и при всех
верных. Это закрывает §19–20 без выдуманных констант, запрещённых §234. WLE —
кандидат в operational person estimator; MLE и WLE нельзя считать одним
численным результатом (§22).

### 268. ПРИВЯЗКА К ШКАЛЕ БМБА `CORE`

**Самый важный раздел для нашей цели и полностью отсутствующий в норме.**

Формула перевода θ → балл БМБА не публикуется. Никакой безупречный движок её
не угадает: математика может быть идеальной, а баллы всё равно не совпадут с
реальными. Единственный путь — эмпирический линкинг.

Процедура:

1. Собрать учеников, у которых есть **и** реальный сертификат БМБА, **и**
   прохождение нашего пробника. Минимум 100–150 на предмет.
2. Common-person linking (§130 — вот где он нужен): найти `A` и `B` в
   `[ Score_BMA = A·θ_наш + B ]`.
3. Пороги уровней A+/A/B+/B/C+/C **не** выводить bookmark-процедурой с
   экспертами (§132 нам поэтому не нужен) — они заданы извне официальными
   порогами БМБА.
4. Заложить критерий приёмки: **MAE** между нашим прогнозом и реальным баллом
   плюс **доля совпадения уровня**. Без этого «соответствие БМБА» — слова.

Пока линкинга нет, любой показанный балл — внутренняя величина платформы, и
называть его баллом сертификата нельзя.

### 269. ТАБЛИЦА RAW → θ → БАЛЛ → УРОВЕНЬ `CORE`

При полных данных в Rasch θ зависит **только от сырого балла** (§7–8). Значит
для каждой фиксированной формы таблица считается один раз:

```
верных → θ → SE → балл → уровень
```

Это быстро, детерминированно и аудируемо — и фактически так и работает БМБА. В
норме этого нет, а production упрощается в разы: выдача балла становится
поиском по таблице, а не прогоном оценки на каждый запрос.

Условие применимости: полные данные и одна форма. Как только появляются
пропуски с разной политикой или адаптивность, таблица перестаёт быть
достаточной.

### 270. DIF ПО ЯЗЫКУ ТЕСТА `CORE`

§60 описывает DIF абстрактно, §65 — по филиалам. У нас есть конкретный и
обязательный случай: **одно задание на узбекском и на русском**. Перевод меняет
сложность, и это не гипотеза, а типовой источник смещения.

Обязательный шаг контроля качества: для каждого задания, существующего в двух
языках, считать DIF между языковыми группами при сопоставимой θ (§60–64).
Найденное — флагом на разбор, не на автоудаление (§223).

### 271. СБОРКА ФИКСИРОВАННЫХ ФОРМ `CORE`

Blueprint в норме описан только внутри CAT (§151–152), то есть в разделе,
который у нас `FUTURE`. Для линейных пробников нужен свой модуль сборки:

- соответствие структуре БМБА — число заданий, распределение по темам;
- целевая test information function (§28) в диапазоне способностей
  выпускников;
- **параллельность вариантов между собой** — иначе один пробник окажется легче
  другого, и ученик увидит «скачок» балла там, где уровень не менялся.

### 272. АНАЛИЗ ДИСТРАКТОРОВ `CORE`

Для закрытых заданий нужна статистика по каждому варианту ответа:

- доля выбравших;
- средняя θ выбравших.

Главный инструмент автора заданий: находит ошибки в ключе и «мёртвые»
дистракторы, которые не выбирает никто. §221 (key error) без этого работает
вполсилы — он констатирует проблему, но не показывает, где именно.

### 273. ГРАФИЧЕСКИЙ ITEM FIT `CORE`

Разбить учеников на 5–8 групп по θ и для каждой сравнить наблюдаемую долю
верных с ожидаемой `P(θ)` из §37.

Один такой график говорит о задании больше, чем Infit и Outfit вместе, и
понятен методисту без психометрического образования. MNSQ (§41–44) сжимает всю
картину в одно число и теряет форму расхождения.

### 274. ФЛАГИ УРОВНЯ УЧЕНИКА `OPTIONAL`

§174 честно говорит: Rasch не занимается обнаружением списывания. Платформе тем
не менее нужны флаги на просмотр — **не как обвинение**:

- person misfit, `lz`-индекс (§114);
- аномально быстрые ответы (§77);
- паттерн «сложные верно, лёгкие неверно».

### 275. ОТЧЁТ УЧЕНИКУ `CORE`

Норма заканчивается на «final decision» (§260) — а ученику нужен результат.
Минимум:

- балл по шкале БМБА;
- доверительный интервал, ±SE в баллах, а не в логитах (§32);
- уровень;
- сколько не хватает до следующего уровня;
- разбор по темам.

Продуктовая часть, но именно она и есть продукт.

### 276. ПОЛИТИКА КАЛИБРОВКИ БАНКА В БОЕВОМ РЕЖИМЕ `CORE`

§159–160 описывают field-test pipeline, но без чисел. Для production нужны
конкретные пороги:

1. Новое задание ставится field-test позицией внутри реального пробника и **не
   влияет на балл ученика**.
2. Накопление ответов до порога — ориентир §166 выше, ≥250–300.
3. Калибровка, проверка fit и DIF.
4. Промоушен в active только после прохождения порогов; иначе — на доработку.

Пороги должны быть записаны как конфигурация с версией (§109), а не жить в
головах.

### 277. ЧЕГО СОЗНАТЕЛЬНО НЕТ `FUTURE`

- **2PL / 3PL / 4PL** — БМБА считает по Rasch. Добавить discrimination или
  guessing значит разойтись с реальными баллами; §187 и §238 это запрещают, и
  правильно, что моделей в норме нет.
- **LPCM** — это LLTM для политомных заданий, а сам LLTM `FUTURE`.
- **Saltus, hybrid Rasch** — модели изучения развития, не сертификации.
- **MST** — экзамен линейный. Если появится адаптивный тренировочный режим, MST
  практичнее CAT, но это отдельный продукт.
- **Kolmogorov–Smirnov, Cressie–Read** — Infit/Outfit плюс Andersen LR
  достаточно; графический fit (§273) полезнее.
- **Vertical scaling** — одна популяция (выпускники), одна шкала на предмет.
- **MCAR / MAR / MNAR формально** — статусов OMITTED и NOT_REACHED (§73–74)
  достаточно. Но нюанс, который надо прописать явно, иначе сделают наоборот:
  **в режиме экзамена пропуск = 0 баллов**, как у БМБА. Логика «missing ≠
  wrong» из §73 относится **только к калибровке**, не к выдаче балла ученику.
- **Generalizability theory** — только для rater studies, а их закрывает MFRM.
- **Автогенерация и клонирование заданий** — content-модуль, не движок.
  Единственное правило для движка: **клон ≠ оригинал по `b`**, клон калибруется
  заново.
- **Multidimensional CAT** — не нужны ни MDRM, ни CAT.

## L.1 подтвердил, что этап 1 шёл в правильную сторону

ТЗ формулирует отчётную трансформацию **линейной по θ** и ни слова не говорит
про Z-стандартизацию:

```
S = A_scale · θ + B_scale        (L.1)
```

Наша формула после этапа 1 — ровно этой формы. При `μ = 0, σ = 1`

```
T = 50 + 10·(θ − μ)/σ  =  10·θ + 50        то есть A = 10, B = 50
```

Это не совпадение, а один и тот же объект: `A = 10/σ`, `B = 50 − 10μ/σ`.
Важно другое — **до этапа 1 наша формула не была вида L.1 вообще**: μ и σ
брались из когорты, поэтому `A` и `B` менялись с каждым составом сдавших, а
трансформация не была ни фиксированной, ни версионируемой. L.1 требует
именно фиксированной и версионированной, а R.3 говорит, откуда взять `A` и
`B` — из линкинга с настоящими сертификатами. Наши `A = 10, B = 50` — это
честный placeholder на месте, где по норме стоят два оценённых числа.

## Калибровка не отделена от оценки ученика — корень остальных проблем

E.1 начинается словами «Калибруем b_i **отдельно** от оценки θ ученика», а
20.1 шаг 3 — «Загрузить калиброванные b_i **нужной версии**». У нас наоборот:
[/api/rasch/recalculate](../src/app/api/rasch/recalculate/route.ts) на каждом
вызове заново прогоняет `estimateRasch` по всем сдавшим и **перезаписывает**
калибровку `upsert`-ом.

Отсюда всё сразу:

- **b меняется от состава сдавших.** Новая сдача сдвигает сложности всех
  заданий, а с ними θ и балл каждого, кто сдавал раньше. Для открытых моков
  пересчёт запускается прямо из браузера при сдаче
  ([mock/[id]/page.tsx:264](../src/app/mock/[id]/page.tsx#L264)) — это
  ровно то, что §239 и P.2 называют молчаливым историческим пересчётом.
  На проде пока не выстрелило: оба реальных теста были с отложенной
  публикацией, поэтому калибровались один раз (обе — 2026-09-06 08:30).
  Путь открыт, случай не наступил.
- **Предыдущий балл невоспроизводим** (§110, §198, P.4): снимка данных нет,
  прежние `b` затёрты, `data_snapshot_id` не существует.
- **У каждого теста свой произвольный нуль.** `mean(b) = 0` до десятого знака
  в обоих тестах — B.5 прямо предупреждает: «Зафиксировать и хранить
  конвенцию — иначе θ несопоставимы между калибровками». Прогресс за месяц
  измерить нельзя, пока нет якорей (модуль K).
- **Выборка втрое меньше нормы.** E.8 требует ≥250–300 валидных ответов на
  задание; у нас 36 и 54. Значит `SE(b)` порядка 0.3–0.4 логита — то есть
  ±3–4 балла шкалы — и это ещё до линкинга.

Правильный порядок по ТЗ: калибровать `b` → проверить качество → **APPROVED,
иммутабельный снимок** → считать учеников против замороженных `b` методом WLE.
Это этапы 2–4, и они же снимают четыре пункта выше разом.

## Почему баллы повторяются — и что на это влияет

Вопрос владельца: «почему баллы очень близкие, в системе Раша все баллы по сути
уникальные, а у тебя одно и то же повторяется». Ответ измерен, и он отменяет
часть очевидных идей.

**Повторы — теорема, а не дефект.** При полных данных число верных ответов
является достаточной статистикой для θ (B.6): одинаковое число верных даёт в
точности одинаковую способность, независимо от того, какие задания решены. На
проде разброс θ внутри такой группы — **4·10⁻¹⁶**, то есть шум двоичной дроби.
На 55 заданиях возможных баллов физически не больше 56, и все 36 ответили на
все 55. Именно поэтому БМБА и публикует таблицу «сырой балл → балл» (R.6):
отображение это справочник, а не непрерывная функция.

**Уникальные баллы были бы ложной точностью.** SE считалась на реальных
сложностях: ±3,2–4,6 балла, а статистически различимы лишь **33%** пар работ.
Балл 31,4 и балл 32,1 — один результат.

**Частичный кредит и PCM здесь почти ничего не дают** — это главный вывод,
проверенный по данным банка:

| тип | заданий | длина ключа | есть ли структура для частичного балла |
|---|---|---|---|
| `single_choice` | 123 | 1 | нет по природе |
| `short_text`, `numeric`, `math_expression` | 34 | — | нет по природе |
| `matching` | 6 | **1** | нет: в этом проекте это один выбор, а не набор пар |
| `multiple_choice` | **1** | 2 | да |
| `essay` | 1 | — | да, но считается вне модели |
| `ordering`, `table_completion` | **0** | — | таких заданий в базе нет |

То есть частичный кредит применим к **одному заданию из 164**. Импорт намеренно
делает «одно отвечаемое задание на вопрос» (`mock-import-prompt.ts:36-37`),
поэтому части a/b математики БМБА приезжают отдельными вопросами — а это для
Раша не хуже PCM, а лучше: два дихотомических наблюдения дают столько же
различных сырых баллов, сколько одно задание с тремя категориями.

Отдельно: на том единственном `multiple_choice` **28 из 54 выбрали хотя бы один
верный вариант и получили ноль** (ключ требует точного совпадения множеств).
Это несправедливо в сыром балле, но на уровень не влияет вообще — модель смотрит
на `is_correct`, а не на `points_earned`.

**Что действительно влияет.** Измерено на 300 синтетических учениках с
распределением реальной когорты:

| вариант теста | различных баллов на 300 | SE | различимых пар |
|---|---|---|---|
| **сейчас** (55 заданий, центр сложности 0) | 34 | ±3,5 | 51% |
| **нацеленный** (те же 55, центр сдвинут к −1,84) | **45** | ±3,3 | 56% |
| **вдвое длиннее** (110 заданий, сложности те же) | **63** | ±2,5 | 63% |

Нацеливание даёт +32% различных баллов и не стоит ничего — надо лишь брать
задания по силам когорте. Удвоение длины даёт +85% и снижает погрешность с 3,5
до 2,5 балла, но это вдвое более длинный тест.

Причина видна в самих числах: сейчас тест точнее всего на θ = −0,4 (балл 46), а
когорта сидит на θ = −1,84 (балл 31,6) — теряется **24% информации**. По силам
когорте **3 задания из 55**, а на 35 из 55 шанс верного ответа ниже 25%.
Ученики скучиваются в нижней части шкалы и используют 34 из 56 возможных
значений вместо 45.

Вывод для плана правок: PCM (модуль J) остаётся нужен ради сочинения и ради
будущих политомных заданий, но **как средство различить учеников он не
работает**. Работает таргетирование (D.9) и длина теста.

## PCM: математика есть, данных для неё нет

Математика модуля J реализована и покрыта тестами —
[rasch-pcm.ts](../src/lib/rasch-pcm.ts): вероятности категорий (§J.2),
ожидаемый балл и дисперсия (§J.4), информация как дисперсия (§J.9),
политомные Infit/Outfit (§182–184), разупорядоченность порогов (§J.6) и
оценка порогов τ_ik **по likelihood** (§J.8 = §180). Дихотомический случай —
частный: две категории дают в точности `P(θ,b)` и `P(1−P)`, это закреплено
тестом. Пороги восстанавливаются из порождённых ими же данных, и отдельно
проверяется само уравнение оценки: наблюдённое число дошедших до категории k
равно ожидаемому.

**Но завести сочинение в модель на текущих данных нельзя.** Не «трудно» —
математически невозможно:

| Задание | Категорий | Наблюдений по категориям | Оценимо |
|---|---|---|---|
| сочинение по узбекскому (24 балла) | 25 | **все 54 работы в категории 0** | нет |

§J.5 требует наблюдений в каждой категории, §219–220 — исключать задание, на
котором все ответили одинаково. При нуле дошедших до категории k уравнение
оценки `Σ 1{x≥k} = Σ P(x≥k)` не имеет корня: τ_k уходит в +∞. Поэтому
`estimateThresholds` возвращает статус `EMPTY_CATEGORY` и **пустой** список
порогов — подставить сюда «пропорцию от максимума» значило бы нарушить §180
прямо в той функции, которая его реализует.

Что нужно, чтобы разблокировать: **градуированные сочинения** — работы,
получившие ненулевые и различные рубриковые баллы. Сколько именно, задаёт
§E.8: для политомных заданий больше, чем 250–300 на задание, и нужны
наблюдения **в каждой** категории. При 25 категориях это заметный объём, и
разумнее сперва сократить рубрику (§J.7 — явным решением с версией).

## Таблица перевода сочинения и деление на два — не баг веса

Проверено по данным и по документу, потому что от этого зависят баллы 54
живых работ:

- **сочинение было предъявлено** — строка ответа есть у всех 54, статус не
  `NOT_REACHED`;
- **никто его не написал** — 52 работы с пустым текстом, у остальных двух

  построчно закреплён тестом;
- **деление на два — это среднее арифметическое двух разделов** из той же
  методики: «birinchi va ikkinchi bo'limlarning o'rtacha arifmetik qiymati
  umumiy ball sifatida qabul qilinadi» (стр. 4).

То есть низкие баллы получились из ненаписанного раздела весом в половину
оценки, а не из потерянного веса на сыром слое. Убрать деление — значит
не «починить баг», а **переопределить методику Агентства**: 54 балла вырастут
с ≈26 до ≈52, и буквы поменяются. Это открытое решение владельца (часть V),

## Балл зависел от когорты — исправлено на этапе 1

```
Замер до правки, 2026-09-08:
Mock Matematika    55 заданий   mean(b) = 0.0000000000   mean(θ) = −1.836   верных 23.3%   ср. балл = 66.67
Ona Tili           49 заданий   mean(b) = 0.0000000000   mean(θ) = −1.090   верных 35.4%   ср. балл = 33.34
```

**Что было.** Балл считался Z-стандартизацией по когорте ТОГО ЖЕ теста, то есть
люди измерялись относительно самих себя. Средний T всегда выходил ровно 50, а
средний балл — 66.67 из 100. Математика решила 23.3% заданий, оказалась заметно
ниже своего пула (θ = −1.836) и получила те же 66.67; когорта, решившая 5%,
получила бы столько же. Прогресс между месяцами измерить было нельзя, а сильная
когорта понижала балл каждому. Нарушались §136–137: балл не был функцией одной
θ.

**Что оказалось важным.** Методика Агентства (стр. 1–2) предписывает ровно
`Z = (θ−μ)/σ, T = 50 + 10Z` — формула была верная. Ошибка была в том, **какие μ
и σ** брать: БМБА стандартизует по национальной популяции, большой и
неизменной, а мы — по тем же тридцати шести, которых измеряли.

**Что сделано.** μ и σ вынесены в [reference-population.ts](../src/lib/reference-population.ts)
как версионированная конфигурация; формула Агентства не менялась. Побочно
исчезла молчаливая подмена разброса при вырожденной когорте, нарушавшая §233 —
подменять стало нечего.

Точка отсчёта — **нулевой эталон** (`μ = 0, σ = 1`, версия `v2-zero`):
50 баллов по T означают способность вровень со средним заданием теста. Ноль не
произволен — `estimateRasch` центрирует сложности через `recenter()`.

Сначала эталоном были заморожены фактические сдачи 2026-09-06 — тогда уже
показанные баллы совпадали один в один и историю не приходилось трогать. Но
эталоном при этом становились те, кто решил 23% и 35%, и абсолютный уровень
оставался завышенным: за половину решённого теста выходило 90 баллов. Владелец
выбрал правдоподобие абсолютного уровня:

| верных | было | стало |
|---|---|---|
| 15% | 44.4 | **19** |
| 28% | 61.4 | **36.6** |
| 53% | 90.4 | **69.9** |
| 78% | 100 | **95.4** |

Ценой стала правка задним числом. Миграция 091 пересчитала все 90 работ:
математика 66.7 → **42.5** (33 из 36 стали «Ниже C», 28 сменили букву),
узбекский 33.3 → **26.2**. Пересчёт **создал 90 ревизий** с прежними
значениями и версией шкалы, а не переписал молча (§239).

**Что этим НЕ решено.** Абсолютной привязки к шкале БМБА по-прежнему нет: она
выводится только эмпирическим линкингом (§268). Нулевой эталон — тоже
осознанный placeholder; после линкинга он заменяется одним преобразованием
`A·θ + B`. До линкинга менять μ и σ вручную нельзя: любая правка сдвинет все
баллы разом и потребует новой ревизии.

Остаётся нерешённым и второе: **каждый тест центрирует шкалу сам** —
`mean(b)` ноль до десятого знака в обоих тестах, у каждого свой произвольный
нуль (§228, §129). Сопоставимость между формами даёт только этап 4.

# Часть V. Решения владельца — не менять, не обсудив

## Расхождения ТЗ v1.0 с прежними решениями — разобраны 2026-09-08

ТЗ принесло шкалу и пороги, которых в v4.0 не было, и в трёх местах они
расходились с тем, что уже стояло в коде. Все три закрыты; ничего не менялось
молча, каждый пересчёт создал ревизии.

### 1. Отчётный балл — РЕШЕНО: 75 во всех предметах

§0.3 говорит «максимум 75, не 100». Прежнее решение от 2026-09-05 — «англ 75,
остальное по 100». Владелец выбрал **75 везде**.

Спор был не косметический, хотя выглядел так. Буква считается от T-шкалы, а
балл показывался растянутым до ста, и числа расходились. На проде это
выглядело буквально:

| показано | T | буква |
|---|---|---|
| 77.2 из 100 | 57.9 | B |
| 63.0 из 100 | 47.3 | C |
| **60.3 из 100** | 45.2 | **«Ниже C»** |

Шестьдесят баллов из ста означало «сертификата нет», потому что порог C = 46
задан на T-шкале. Теперь балл и порог — одно число: 47.3 → C.

Заодно закрылся §237 (NO CROSS-SCALE MIXING). Пока шкал было две, средние по
группе, учителю и филиалу считались в **процентах** от максимума — и «средний
балл» был процентом, а не баллом; у английского 60 из 75 попадало в среднее
как 80. Миграция 092 перевела на баллы и `averageCertificateScore`, и три
SQL-функции (`get_branch_overview`, `get_my_rating`,
`get_my_class_subject_ranking`).

Цена: каждый из 90 баллов умножен на 0.75 — математика 42.5 → **31.9**,
узбекский 26.2 → **19.7**. **Буквы не изменились ни у одной работы** (они и
раньше считались от T), доля от максимума тоже. 90 ревизий с причиной
`certificate_scale_75_all_subjects`.

Что осталось на будущее: R.3 подбирает `A_scale`/`B_scale` против настоящего
балла БМБА и R.5 мерит MAE в баллах той же шкалы. То есть шкала сравнения при
линкинге обязана совпадать с той, в которой отчитывается настоящий сертификат
по этому предмету, — а не быть «нашими 75» по умолчанию. Проверять это на
этапе 5, а не сейчас.

### 2. Буква у границы — РЕШЕНО: полуоткрытые интервалы, без округления в полосу

Таблица §0.3 задаёт полосы с точностью 0.1 (`65 – 69.9 → A`,
`60 – 64.9 → B+`), а `gradeLevelFromScore` округлял T до ближайшего целого по
прежнему решению «если ближе к 65 — значит 65». На T из `[64.5, 65)` правило
выдавало `A` там, где норма требует `B+`.

Правило заменено на полуоткрытые интервалы по точному значению:

```
[0,46) ниже C   [46,50) C   [50,55) C+   [55,60) B
[60,65) B+      [65,70) A   [70,∞) A+
```

Верхняя полоса открыта справа, и это закрывает дыру в самой таблице ТЗ: между
«> 70 → A+» и «65 – 69.9 → A» балл ровно `70.0` не покрыт ничем. Здесь он даёт
A+ по построению.

**Ни одна из 90 букв не изменилась** — проверено запросом до правки: T не выше
57.90, в спорные окна не попал никто.

Один нюанс, которого ни в ТЗ, ни в прежнем решении не было и который поймал
тест. Балл показывается с одной десятой, поэтому полоса берётся **от
показанного балла**, а не от неокруглённого T: иначе ученик с T = 64,96 увидел
бы «65,0» рядом с буквой B+. L.8 требует ровно этого — «чтобы у границ уровней
не было расхождений». Порядок: θ → точное T → округление до 0.1 → полоса.
Округление осталось одно (`roundScore`), и после него ничего не пересчитывается.

### 3. Сочинение — РЕШЕНО частично: PCM это направление, а деление на два не баг

Направление подтверждено: сочинение — политомное задание, и по модулю J его
место **внутри** модели, с порогами `τ_ik`, а не в таблице перевода
([native-cert.ts](../src/lib/native-cert.ts)). Это этап 8.

А вот утверждение «деление на два — ошибка веса на сыром слое» данные не
подтвердили. Проверено на 54 работах по узбекскому:

- строка ответа на сочинение есть **у всех 54** — раздел был предъявлен, это
  не `NOT_REACHED` (A.4);
- баллов за него **ни у одного**, и текст пустой у 52; у двух оставшихся
  максимальная длина ответа — **9 символов**;
- по таблице документа ноль даёт ровно 0 («несданная работа не получает нижнюю
  границу шкалы», стр. 3–4), и это напечатано в бумаге, а не наш вывод.

То есть балл делится на два потому, что раздел весом в половину оценки не
написан, — а это политика оценивания из A.3 («в режиме экзамена пропуск не
даёт баллов»), а не потерянный вес. Достижимый максимум при этом не падал: за
написанное сочинение раздел даёт до 75.

Настоящая проблема здесь другая и она не психометрическая: **сочинение на 24
балла пропустили 54 из 54**. Пятьдесят четыре независимых решения выбросить
почти половину экзамена — маловероятны. Вероятнее, ученики его не увидели или
не поняли, что его надо писать. Плюс структурная деталь: в тесте **один
раздел**, «Test topshiriqlari», и сочинение лежит последним вопросом внутри
него, тогда как методика описывает два блока. Разбираться с этим надо в
продукте и в импорте теста, а не в шкале.

Сырой вес сочинения (число 24 и структура блоков) сверять по предметной
спецификации БМБА — её у нас нет.

## Действующие решения

Источник — `Baholash_mezoni.pdf` и решения владельца.

- **Итоговый балл: 75 во всех предметах** — та же шкала, что у модели Раша и
  что у порогов уровней ([certificate-scale.ts](../src/lib/certificate-scale.ts)).
  Прежние «100 у общеобразовательных» отменены 2026-09-08, миграция 092.
- **Уровень A+..C — полуоткрытые интервалы по ТОЧНОМУ баллу**, без округления
  в полосу: `[46,50) C`, …, `[70,∞) A+`. Пороги 70/65/60/55/50/46 — на той же
  шкале 75, что и балл. Буква считается от раш-меры θ, а не от взвешенной
  суммы баллов за задания: веса заданий в измерение не входят вовсе.
- **Балл показывается с одной десятой, и округление стоит ПОСЛЕ выбора полосы**
  (§202–203, решение владельца от 2026-09-09). Порядок: θ → точный балл →
  полоса → округление для показа. Цена: у балла в пределах 0,05 ниже порога
  показанное число может выглядеть достигшим порога, а буква — нет. Суммарно
  это 0,30 балла из 75 (0,4% шкалы), и ни одна из 56 строк таблицы математики
  в это окно не попадает. Убрать расхождение полностью можно, округляя показ
  ВНИЗ вместо ближайшего: пороги кратны 0,1, поэтому floor никогда не переносит
  балл через порог. Отдельное решение, пока не принято.
- **Точка отсчёта шкалы — нулевой эталон** (`μ = 0, σ = 1`): 50 баллов по T
  означают способность вровень со средним заданием теста. Выбрано
  правдоподобие абсолютного уровня, а не сопоставимость с сентябрьскими
  баллами; ценой стал пересчёт 90 работ с ревизиями (миграция 091). Менять μ и
  σ до линкинга §268 нельзя.
- **Сумма баллов за задания свободная.** `normalizePointsTo75` и гейт «сумма =
  75» сняты специально (`design/FIX.md`, «Две шкалы 75»). Приводить сумму к 100
  нельзя — это вернуло бы самодельную шкалу и нарушило §235.
- **Родной язык — два раздела**: тест по Рашу плюс сочинение по 24-балльному
  критерию, итог — среднее арифметическое ([native-cert.ts](../src/lib/native-cert.ts)).
  Отсюда «половина балла» у тех, кто сочинение не написал: это политика
  оценивания из A.3, подтверждённая данными (см. разбор выше), а не потерянный
  вес. Место сочинения внутри модели как PCM — этап 8.
- **Средние — простым средним по работам**, как у групп и учителей.
- **Placement/Diagnostic не показывает разбор по вопросам** никому, даже
  админу, — только итоговый процент.
- **Проценты остаются только у вступительных тестов**; у моков везде баллы.

# Часть VI. Порядок правок

Пересобран под ТЗ v1.0. Каждый этап опирается на предыдущий; порядок выбран
так, чтобы сначала перестать портить данные, потом начать измерять точнее, и
только потом добавлять диагностику.

- **Этап 0 — этот документ.** Готово.

- **Этап 1 — балл перестаёт зависеть от когорты. Готово.** μ и σ вынесены в
  версионированную конфигурацию
  ([reference-population.ts](../src/lib/reference-population.ts)); формула
  Агентства не менялась. Точка отсчёта — нулевой эталон (`μ = 0, σ = 1`), то
  есть `S = 10·θ + 50` — уже нужного L.1 вида. Миграция 091 пересчитала 90
  работ и создала ревизии (§239). Осталось из этапа: таблица
  raw → θ → балл → уровень (R.6).

- **Этап 2 — перестать молча пересчитывать прошлое.** Самое дешёвое из
  крупного и единственное, что прямо сейчас может испортить уже показанный
  балл. Развести калибровку и оценку ученика (E.1): снимок калибровки
  (E.4 / §110) со статусом `DRAFT → APPROVED` (P.1), иммутабельность после
  утверждения (§229), ссылка из результата на версию калибровки и estimator-а
  (E.3 / §109, P.3 provenance). Убрать пересчёт всей группы при каждой сдаче
  открытого мока. Серверная подстраховка вместо fire-and-forget из браузера:
  работа без измерения обязана нести **статус**, а не пустоту (§215, §217).

- **Этап 3 — точность и статус измерения.** `SE(θ)` и `SE(b)` (D.4, E.10),
  информация теста и TIF (D.3), сохранение `converged`/`iterations`,
  `INSUFFICIENT_INFORMATION` и `NON_CONVERGED` вместо молчаливого результата
  (§217, §233, C.4), `quality_status` персоны и задания (N.3–N.4),
  separation и reliability (N.5). **Переход на WLE как основной оценщик θ**
  (C.8) с формулой Warm и отдельной версией estimator-а — норма требует
  именно его, и он же убирает потребность в поправке 0.3 для крайних баллов.
  Зафиксировать выбор estimator-а калибровки (E.1 рекомендует CML или MMLE;
  если остаётся JMLE — записать решение и добавить поправку `(L−1)/L`).

- **Этап 4 — банк и якоря.** Общий банк, якоря в формах, linking (K.1–K.10),
  связность банка (E.11), `equating_uncertainty` (K.9), отказ
  `LINKING_NOT_IDENTIFIABLE` при недостаточной связности (K.10). Только после
  этого «прогресс за месяц» — настоящая величина, а не сравнение двух
  произвольных нулей. Сюда же межъязыковая идентичность задания, без которой
  модуль H неисполним.

- **Этап 5 — привязка к БМБА (модуль R).** Сбор учеников с реальными
  сертификатами (R.2: 100–150 на предмет, покрыть все уровни), оценка
  `A_scale`/`B_scale` (R.3), приёмка по числам R.5: MAE ≤ 2–3 балла,
  совпадение уровня ≥ 85–90%, на held-out, с отдельной проверкой у границ.
  До этого этапа утверждение «как в Миллий сертификате» проверить нечем.

- **Этап 6 — диагностика.** Infit/Outfit/ZSTD (F.4–F.9), point-measure (F.11),
  графический item fit (F.12), Yen Q3 по существующему `group_key` (G.2),
  DIF uz/ru с effect size и поправкой на множественность (H.3–H.6),
  размерность и residual PCA (G.3–G.4), дистракторы (R.7), дрейф якорей
  (K.6–K.7) и заданий (I.1). Обнаружение и флаги; **удаление заданий —
  никогда автоматически** (§222–224).

- **Этап 7 — пропуски.** OMITTED и NOT_REACHED (A.3–A.4) с явным флагом
  `missing_policy = EXAM | CALIBRATION`. Помнить: в режиме экзамена пропуск не
  даёт баллов, «missing ≠ wrong» — только для калибровки.

- **Этап 8 — PCM (модуль J).** Пороги `τ_ik`, кривые категорий,
  disordered thresholds, collapsing только явно (§240). Сюда переходит
  сочинение на 24 балла. Позиция в очереди — не по важности (ТЗ помечает J
  как CORE), а потому что частичного кредита в данных сегодня нет: **0 из
  4700 ответов**. Как только появится задание с частичным баллом, этап
  поднимается выше 6 и 7.

- **Этап 9 — сборка вариантов и отчёт.** Field-test на пилотных позициях
  (модуль M), целевая TIF и параллельные формы (D.9, R.7), карта Райта и ICC
  (D.10, D.12), отчёт ученику с ±SE и «сколько до следующего уровня» (R.7),
  MFRM для проверяющих (§87–93, OPTIONAL — только там, где оценивает человек).

## Что сделать до любого этапа

Три решения владельца из части V блокируют смысл, а не код: пока не выбрана
главная шкала (0–75 или 100), правило буквы у границы и судьба деления на два,
любой пересчёт придётся делать ещё раз — с новыми ревизиями.

# Часть VII. Запросы для проверки

Ими получены все числа части IV; ими же проверяется, что правки подействовали.

```sql
-- Каждый тест центрирует шкалу сам: mean_b — ноль до десятого знака.
-- После общей шкалы (этап 4) обязан перестать быть нулём.
select mt.title, count(ic.id) as items,
       round(avg(ic.difficulty)::numeric, 10) as mean_b,
       (select round(avg(mr.rasch_score)::numeric,3) from mock_results mr where mr.mock_test_id = mt.id) as mean_theta,
       (select round(avg(mr.level_score)::numeric,2) from mock_results mr where mr.mock_test_id = mt.id) as mean_score
from mock_item_calibration ic join mock_tests mt on mt.id = ic.mock_test_id
group by mt.id, mt.title;

-- Средний балл — константа 66.67 при любой подготовке когорты.
-- После этапа 1 обязан начать зависеть от того, как решали.
select mt.subject_id,
       sum(mr.correct_answers) || '/' || sum(mr.total_questions) as correct_of_asked,
       round(100.0*sum(mr.correct_answers)/nullif(sum(mr.total_questions),0),1) as pct_correct,
       round(avg(mr.level_score),2) as mean_score
from mock_results mr join mock_tests mt on mt.id = mr.mock_test_id
group by mt.subject_id;

-- Доля неотвеченного, которое уходит в модель как неверное (§73–74).
select q.question_type, count(*) as answers,
       count(*) filter (where ad.selected_answer = 'null' or ad.selected_answer is null) as unanswered
from mock_answer_details ad join mock_questions q on q.id = ad.question_id
group by q.question_type order by answers desc;

-- Testlet-группы, которые модель считает независимыми (§50–55).
select mt.title, q.group_key, count(*) as items_in_group
from mock_questions q
join mock_sections s on s.id = q.section_id
join mock_tests mt on mt.id = s.mock_test_id
where q.group_key is not null
group by mt.title, q.group_key having count(*) > 1 order by items_in_group desc;

-- Есть ли вообще частичные баллы (сегодня 0 — поэтому PCM пока этап 8).
select count(*) as genuinely_partial from mock_answer_details
where coalesce(points_earned,0) > 0 and max_points is not null and points_earned < max_points;

-- Работы без измерения: результат есть, балла нет (§215, §217).
-- Сегодня одна — «Tarix», class_only. Обязана вернуть 0 после этапа 2.
select mt.title, mt.type, count(*) as results_without_score
from mock_results mr join mock_tests mt on mt.id = mr.mock_test_id
where mr.level_score is null and mr.accuracy is not null
group by mt.title, mt.type;

-- Когда калибровался каждый тест. Если calibrated_at обновляется после
-- первого расчёта — значит прошлые баллы пересчитаны молча (§239).
select mt.title, mt.type, count(mr.id) as results,
       min(ic.calibrated_at) as first_cal, max(ic.calibrated_at) as last_cal
from mock_tests mt
left join mock_results mr on mr.mock_test_id = mt.id
left join mock_item_calibration ic on ic.mock_test_id = mt.id
group by mt.id, mt.title, mt.type having count(mr.id) > 0;

-- Веса заданий против дихотомической модели (A.2, модуль J).
select mt.title, q.question_type, count(*) as items,
       min(q.points) as min_pts, max(q.points) as max_pts,
       count(*) filter (where q.points > 1) as multi_point
from mock_questions q
join mock_sections s on s.id = q.section_id
join mock_tests mt on mt.id = s.mock_test_id
group by mt.title, q.question_type order by mt.title, items desc;

-- Буква против балла: сохранённый grade_level обязан получаться из
-- сохранённого level_score действующим правилом (полуоткрытые интервалы).
-- Ненулевой letter_mismatch = рассинхрон, то есть балл или букву меняли в
-- обход общего пути. Заодно видно, что шкала у всех одна.
select mt.subject_id, count(*) as works,
       max(mr.level_score_max) as scale_max,
       round(avg(mr.level_score),1) as avg_score,
       count(*) filter (where mr.grade_level is distinct from case
         when mr.level_score >= 70 then 'A+' when mr.level_score >= 65 then 'A'
         when mr.level_score >= 60 then 'B+' when mr.level_score >= 55 then 'B'
         when mr.level_score >= 50 then 'C+' when mr.level_score >= 46 then 'C'
         else 'below_c' end) as letter_mismatch
from mock_results mr join mock_tests mt on mt.id = mr.mock_test_id
where mr.level_score is not null group by mt.subject_id;

-- Не осталось ли агрегата, который приводит балл к сотне. После миграции 092
-- должно быть три функции и still_percent = false у всех.
select p.proname,
       pg_get_functiondef(p.oid) like '%level_score_max * 100%' as still_percent
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname='public' and p.prokind='f'
  and pg_get_functiondef(p.oid) like '%level_score_max%';

-- Сочинение: писали или пропустили. Различает A.3 (OMITTED — строка есть,
-- баллов нет) и A.4 (NOT_REACHED — строки нет вовсе). На 2026-09-08 по
-- узбекскому: строк 54 из 54, баллов 0, текст пустой у 52, максимум 9
-- символов — раздел предъявили, но не написал никто.
select count(*) as works,
       count(*) filter (where ad.id is null) as no_row_at_all,
       count(*) filter (where coalesce(ad.points_earned,0) > 0) as with_points,
       count(*) filter (where ad.selected_answer is null
                           or ad.selected_answer in ('null','')) as blank,
       max(length(coalesce(ad.selected_answer,''))) as max_len
from mock_results mr
join mock_tests mt on mt.id = mr.mock_test_id
join mock_sections s on s.mock_test_id = mt.id
join mock_questions q on q.section_id = s.id and q.question_type = 'essay'
left join mock_answer_details ad on ad.result_id = mr.id and ad.question_id = q.id
group by mt.subject_id;

-- Ревизии баллов: что и почему правилось задним числом (§239).
select reason, scale_version, count(*),
       round(avg(level_score)::numeric,2) as avg_before,
       max(level_score_max) as max_before
from mock_result_revisions group by reason, scale_version order by reason;
```
